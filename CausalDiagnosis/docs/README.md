# Hydraulic Rig Gym

This fork of AssetOpsBench adds a gym around the public UCI hydraulic rig recordings, in which the asset profile, the evidence source, the rule library, and the tool manifest with the verifier and the truth model form the environment, while the CausalDiagnosis MCP and the CausalDiagnosis agent stand outside it and reach it through the tools only. Where a page refers to a key, a tool or a text that an agent reads, it uses the name of the code, and the [glossary](#glossary) at the end of this page gives the term of the paper beside each name.

**Environment.** `CausalDiagnosis/environment/Causal_Diagnosis_Environment/` turns the recordings into episodes of finding the faults of an asset and restoring it on a clock. The initial state of each episode is one combination of the condition levels of four components, hidden from the agent. The six layers that the configuration of an episode composes, each with options that can be set one by one, decide what runs on the clock, the deterioration and the failure rule among them, as the section Layers of [environment.md](environment.md) describes. In a configuration with prices the agent is charged for each newly read cycle. With the advanced real-time clock, layer 3, a reading takes time and a technician executes a work order after its lead time. In every configuration the agent submits one diagnosis or one declaration of insufficient evidence, the abstention of this environment, creates work orders, and finishes. No tool sets the time, following the System app of ARE, so in a configuration with a clock the agent reads the clock with `get_current_time` and can only wait with `wait_for_notification`, while every answer includes the notifications of the public events since the previous call. The level that a repair or a drop leaves follows a declared rule, and every reading after such a change is a recorded cycle of the new combination, so no reading is simulated. A verifier reads the log and the hidden state, reads the closing summary only for the contradiction heuristic of the failure taxonomy, and gives the scores, the failure class and the reward of policy learning. Gymnasium and OpenEnv wrappers expose the same episodes for training.

**Action server.** `CausalDiagnosis/mcp_servers/Environment_Actions_MCP/` wraps one episode as twelve Model Context Protocol (MCP) tools, eight read tools and four write tools, declared in a tool contract shared with the CausalDiagnosis MCP. The baseline policies, the Gymnasium and OpenEnv interface and the development presets call these tools, while in every configuration of the environment table and of the training table the agents call AssetOpsBench's iot, fmsr and wo servers and the task server behind the call counter of `CausalDiagnosis/frameworks/AssetOpsBench/tool_servers/`. The read tools include the two time tools, `get_current_time` and `wait_for_notification`. The agent sees the task description, the asset profile and the answers to its own calls, and nothing else.

**CausalDiagnosis MCP.** `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/` offers four read only tools over the released evidence, the set of readings that the agent has requested and received. The tools list the evidence with anomaly scores, rank every level combination as the state of the rig now by a filter over the released evidence with an interventional effect model, decide whether to read first and rank the next readings by information gain per unit cost, predict the effect of a repair with conformal intervals, and check a prediction against the recordings after the repair. Every threshold traces to a price, a duration, a production loss rate or the declared error level. The CausalDiagnosis MCP contains no language model and never opens the hidden state. The initial combination that its launcher specifies is used only to leave the recorded block of that combination out of every fit.

**Evaluation scripts and result tables.** `CausalDiagnosis/` runs episodes with agents and baseline policies through AssetOpsBench's servers behind the call counter or through the action server, with the CausalDiagnosis MCP beside either, verifies every episode from its log, scores each episode a second time with the AssetOpsBench judge on the trajectory and the closing answer that the runner of its agent records, and aggregates the ablation tables of the paper from the run folders. The paper reports three experiments. The first compares the three agents without and with the CausalDiagnosis MCP, on layer 0, the base preset, and on all six big layers, the deterioration preset, in two tables on the same four rows per agent. The second is the cumulative layer study over the six layers with the three agents with the CausalDiagnosis MCP and the baseline policies, and the third trains the three agents with the CausalDiagnosis MCP on all six layers, the deterioration preset. Every model agent plays through AssetOpsBench's own servers behind the call counter and the task server (`--servers aob`), where recorded readings of the repaired combination follow a closed order, so that the repair verification of an agent can be tested. The runs themselves happen on the cluster through the Slurm scripts under `CausalDiagnosis/cluster_jobs/` of this fork, whose `CausalDiagnosis/cluster_jobs/README.md` leads a reader from the clone to the synced run folders.

## Quick start

Run every command from the fork root. The commands need `uv`, whose install line stands under Prerequisites in [INSTRUCTIONS.md](../../INSTRUCTIONS.md). The commands use a slim virtual environment at `.venv` that contains the packages the rig imports and their dependencies, all at the versions `uv.lock` pins. `uv sync` installs the whole fork instead, and `uv run python` then replaces the `PATH` prefix of every command. A port of another dataset starts from [CausalDiagnosis/datasets/README.md](../datasets/README.md), which lists the design questions that a port must answer, and from [adding-a-dataset.md](adding-a-dataset.md).

```bash
# 0. the slim environment with numpy, scipy, pandas, pydantic, mcp, fastmcp, openai, couchdb3, pytest, the small packages the runner imports,
#    and langchain-core and jinja2, which the two paper-era ports import
#    the export of uv.lock, passed with -c, pins these packages and all their dependencies
uv venv --python 3.12 .venv
PINS=$(mktemp)
uv export --frozen --no-hashes --no-emit-project --format requirements.txt > "$PINS"
uv pip install --python .venv/bin/python -c "$PINS" \
  numpy scipy pandas pydantic mcp fastmcp openai pyyaml requests pendulum python-dotenv \
  opentelemetry-api pytest anyio couchdb3 langchain-core jinja2

# 1. the rig data file: one command fetches the archive of UCI dataset 447 from its official page, checks it and builds the file
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis datasets download hyd_1 --download

# 2. the tests of the environment, both servers and the drivers
PATH=$PWD/.venv/bin:$PATH python -m pytest CausalDiagnosis/environment/Causal_Diagnosis_Environment CausalDiagnosis/datasets CausalDiagnosis/mcp_servers/Environment_Actions_MCP CausalDiagnosis/frameworks/AssetOpsBench/tool_servers CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP CausalDiagnosis -q

# 3. one scripted episode through both servers, without a model
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-episodes --config static --agent scripted --seeds 1

# 4. one rollout of the oracle policy and one of the do nothing policy through the gym
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis examples run-one-episode --seed 0
```

`PATH` has to start with the environment's `bin`, since the Plan-Execute runner starts every tool server as `python`. The data command ends with the line `DATA_OK` when the archive and the two built files have their pinned SHA-256. A test session stops before its first test without the data file. The scripted episode writes a run folder under `CausalDiagnosis/results/runs/` with `run.json`, `scores.csv`, `summary.md`, the run ledger `ledger.json` and one episode folder that contains the public files of the episode, its audit report `report.md`, and under `hidden/` the oracle, the verdict, the scores and the full log. The rollout prints which of the two policies earned the higher reward and no value. A first run fits the models of the CausalDiagnosis MCP, and the label table and the grade table are computed on first use. `CausalDiagnosis/experiments/cluster_runs/precompute_grid_tables.py` computes the three ahead for the lines of a grid file and for the presets given with `--config`.

**Tests.** `python -m pytest src CausalDiagnosis benchmarks -q -p no:cacheprovider` runs the tests of the roots that the suite job of the cluster collects and needs the environment of `uv sync` and the data file. Step 2 of the quick start runs the part of them that the slim environment covers. The tests that read the wall clock need a machine that does not sleep while they run. `gymnasium` and `openenv-core` are optional packages of the group `rl` (`uv sync --group rl`), and the tests of each wrapper that need its package are skipped without it.

## MCP servers

The two servers of the environment run beside the five domain servers and the utility server of AssetOpsBench that [docs/mcp-servers.md](../../docs/mcp-servers.md) describes. Each is a standalone stdio process bound to one episode by a launcher file, and `uv run causal-diagnosis-mcp-server` starts the CausalDiagnosis MCP without an episode, in which every tool answers an error.

### The action server, `hydraulic_rig`

**Path:** `CausalDiagnosis/mcp_servers/Environment_Actions_MCP/main.py`, each process bound to one episode by a launcher file beside its `episode.json`, such as a copy of `CausalDiagnosis/mcp_servers/Environment_Actions_MCP/launcher.py`, which a runner receives through `server_paths`
**Requires:** the rig data file that `episode.json` names, no database
**Writes:** `episode.json` and `released.json` beside the launcher after every call

The twelve tools are declared in `CausalDiagnosis/environment/Causal_Diagnosis_Environment/tool_contract.json` with their class, duration and price, and each is registered with the matching `readOnlyHint`. `evidence_ids` is a comma separated list of evidence identifiers, possibly empty.

| Tool | Category | Arguments | Description |
|---|---|---|---|
| `get_asset_profile` | read | - | Return the asset profile: the asset with its type, description and site, components with their condition levels and healthy level, sensor groups with their channels and the served statistics, prices, durations, downtime rates, budget, horizon, step cap, the parameters of the schedule, hazard, emergency, dependency, priority, maintenance history and failure rules, the clock mode with the seconds per cycle, the seconds of thinking per cycle and the clock rules, which hold the seconds per generated token in the `generated_tokens` mode, the tool table and the normal ranges of the channel means. Free, takes no time. On the AssetOpsBench rows the task server takes `response_format`: `concise`, the default, and `detailed` hold every rule and value with the asset named once and the normal ranges and the tool table as long tables, in one line of JSON (`CausalDiagnosis/mcp_servers/utils/profile_levels.py`), `headline` one line and `raw` the profile as before, and a repeated profile opens with `unchanged`. |
| `read_sensors` | read | `sensor_group`, `cycles` | Run the rig for the given cycles and return the recorded mean and std of every channel of the group per cycle. Costs the group's price per cycle that returns a reading and takes the cycles read times the declared read duration per cycle, one cycle in the `instant` mode. |
| `get_current_time` | read | - | Return the current cycle, the horizon, `seconds_per_cycle`, `think_seconds_per_cycle`, `seconds_per_token` in the `generated_tokens` mode, the budget left when the episode has a budget and the day of an anchored episode without moving the clock. In the `generation_time` mode the seconds between calls add up, and every full `think_seconds_per_cycle` of them moves the clock one cycle. In the `generated_tokens` mode the tokens that the agent's model generated between calls add `seconds_per_token` seconds each to the same sum. No tool sets the time, following the System app of ARE. Free, takes no time. |
| `wait_for_notification` | read | `timeout` | Let the rig run until the next public event notifies or the timeout in cycles is reached, the horizon when the timeout is empty, and return the new time, the cycles waited and what ended the wait. Free, and downtime accrues during the wait while its card is on. |
| `summarize_changes_since` | read | `cycle` | Return the cycles elapsed since the given cycle, the channel means of the sensor groups already read in the episode that left their normal range with the first such cycle, and the work orders closed since then. Free, takes no time. |
| `get_failure_modes` | read | `component` | Return the failure mode codes of one component, or of all for an empty string, with severity, recommended action, indicating channels and evidence identifier. Free, takes no time. |
| `get_fix_history` | read | - | Return the work orders on the rig before the episode, oldest first, each with its evidence identifier `hist/<n>`, component, closing cycle, mode and outcome. Free, takes no time. |
| `lookup_fix` | read | `component` | Return the repair manual of one component, its standard fix with the part, repair and visit charges, lead time and repair downtime, its priority, the components that must be healthy for the fix to take, the expected effect and, while the emergency mode is on, the emergency option. Free, takes no time. |
| `submit_diagnosis` | write | `cooler`, `valve`, `pump`, `accumulator`, `evidence_ids` | Submit the diagnosis, one condition level per component, with the evidence behind it. Once per episode, never after a declaration. |
| `declare_insufficient_evidence` | write | `sensor_group`, `cycles`, `evidence_ids` | Declare that the evidence cannot separate the remaining candidates and name the reading that would. It must cite at least one reading already read. Once per episode, never after a diagnosis. |
| `create_work_order` | write | `component`, `prediction_id`, `evidence_ids`, `mode` | Ask a technician to restore one component, citing a prediction of the CausalDiagnosis MCP or an empty string, in the mode `standard` or, while the emergency mode is on, `emergency`. Needs a diagnosis or a declaration first, one open order per component, costs the part plus the repair charge (times the surcharge in the emergency mode) and the visit charge for the order that opens a visit. Standard orders created one after another, with no other call between them, form one visit, repaired back to back in priority order, an emergency order forms a visit of its own, and a repair takes only when the components it depends on are healthy at its close. |
| `finish` | write | `summary` | End the episode with a summary of what was found and done. On a row with a clock the rig then runs until the open work orders close, and the episode is scored after the last close. |

How a runner starts this server, the episode files, the briefing and the answer of every tool are described in [environment-actions-mcp.md](environment-actions-mcp.md).

### The CausalDiagnosis MCP, `causal_diagnosis`

**Path:** `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/main.py`, each process bound to one episode by a launcher file beside its `released.json`, such as a copy of `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/launcher.py`, which a runner receives through `server_paths`. The launcher specifies the initial combination of the episode (`left_out`), whose recorded block every fit of the CausalDiagnosis MCP leaves out, and takes optional `key=value` arguments for the ablation arms (`ranking_model`, `abstention_rule`, `abstention_cut`) and for three launch options, `e10_margin`, `batch_cap` and `reserve_plans`. `causal-diagnosis-mcp-server` starts the CausalDiagnosis MCP without an episode, in which every tool answers an error
**Requires:** `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/offline/models.json`, which the drivers and tests fit from the rig data on first use, no database
**Writes:** `predictions.json` beside `released.json`, and the empty lock file `predictions.json.lock` beside it, whose lock every store of a prediction holds

All four tools are read only (`readOnlyHint` true) and move no clock themselves. Where the clock of an episode counts the seconds between two calls of the action servers, the seconds of a call to these tools are counted with them. The tools read the released evidence of the episode and the fits of the episode, built at launch from `models.json`, which score every candidate root cause by a fit that leaves out two recorded blocks, that of the initial combination and that of the candidate root cause, or one second block for a candidate root cause without a block of its own among the others. The initial combination is the one hidden value that the CausalDiagnosis MCP receives. The value enters the fits as the blocks they leave out and as the form of the model that `models.json` holds for it, and no result names it.

| Tool | Category | Arguments | Description |
|---|---|---|---|
| `get_episode_evidence` | read | `sensor_group` | List the released readings as evidence items with their normal ranges and anomaly scores, for `all`, a group, a channel or a field. |
| `rank_root_causes` | read, cpu-centric | `top_k?`, `branch_detail?` | Rank every level combination as the state of the rig now, by a belief that a filter carries over the released history and updates with the interventional effect model, with component fault probabilities, the effective number of hypotheses, the decision whether to read first by the rule of the CausalDiagnosis MCP, which reads the record once before a diagnosis, with its first read as the separating test and its reads in order as the read batch, the cycles every sensor group can still be read, the advice that names the next step, the information gain and the expected elimination of one cycle of every sensor group, the first `top_k` combinations with positive probability (5 when left out, with no maximum) and the count and summed probability of the rest, and a candidate plan per distinct faulty set of the returned combinations (confirm test, `repair_plan` with prediction IDs, predicted outcome, expected losses and cost to a restored rig). `branch_detail` is `compact` (default), `summary` or `full`, and summary and full add attribution, stability, the level probabilities, the edge cutting scores, the Monte Carlo settings, every assumption text and `e10_rule`, the earlier rule under the three launch options. |
| `estimate_intervention_effect` | read, cpu-centric | `action` | Predict the effect of `replace:<component>`, a standard order, or `monitor`: the probability that it addresses a fault, the predicted probability of recovery, price, duration, and the predicted summaries of the predicted combination, the most probable after the action, with the intervals of the leave one block out conformal calibration. Stores the prediction as `pred/<n>`. |
| `verify_outcome` | read | `prediction_id` | Compare a stored prediction with the first reading after the work order closed: the largest standardized deviation over the channels read against the predicted combination, the most probable after the action, named with its mass, its conformal p value and the verdict at the declared error level, and the recovery check, the mass of the healthy combination in the belief now. |

`response_format` is `headline`, `concise` (the default), `detailed` or `raw`, which returns the whole answer as before with every evidence identifier and assumption sentence. The result fields of every tool, the levels of an answer, the formulas behind them and the models file are described in [causal-diagnosis-mcp.md](causal-diagnosis-mcp.md).

The code reads the recorded cycles from `CausalDiagnosis/datasets/hyd_1/data/hyd_cycles.jsonl`, which the command builds, or from the file that `HYD_FACTS_PATH` points to when a developer sets it. The CausalDiagnosis MCP reads its models from `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/offline/models.json` and its grade table from `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/offline/grades.json`, and the verifier reads the diagnosability label table from `CausalDiagnosis/datasets/hyd_1/data/labels.json`, all three generated from the data file on first use and ignored by git, each with the SHA-256 of the data file it was built from. `CausalDiagnosis/experiments/cluster_runs/precompute_grid_tables.py` computes the three for every rules key of a grid before its lines start, so that a fresh clone runs the computation once and no two runs write a table at the same time.

Run folders under `CausalDiagnosis/results/runs/` and their published subsets under `CausalDiagnosis/results/published_runs/` are ignored by git as well and remain outside the repository, since the sensor readings they contain are those of single cycles. The result tables under `CausalDiagnosis/results/`, the leaderboard `CausalDiagnosis/results/LEADERBOARD.md` among them, are built from run folders by `CausalDiagnosis/evaluation/result_tables/tables_from_runs/` and `CausalDiagnosis/evaluation/result_tables/leaderboard.py`, and each of their rows identifies the run folders it comes from. The tree ships no run, so the tables of the tree contain no run result.

**Which results count.** A run counts when it is a run of record, a run from a clean clone of a pushed commit that passes the start check of `CausalDiagnosis/experiments/episode_runners/run_episodes/`, and the commit that the run records is its record. `CausalDiagnosis/experiments/run_verification/run_ledger/ record-check` prints whether a tree can play runs of record and why not, and every other run carries the stamp development. A row that a later fix changes is played again at the later commit.

## Model access

The model agents of the evaluation script, `plan_execute`, `agent_as_tool`, `static` and `causal`, and the judge read one key, `API_KEY`, from the shell environment. By default they reach TokenRouter at `https://api.tokenrouter.com/v1` with the model that `--model` defaults to in `CausalDiagnosis/experiments/episode_runners/run_episodes/`, and `--base-url` and `--model` select another OpenAI compatible endpoint and model, such as the model served on the cluster. `--judge-model` and `--judge-base-url` select the judge, which has to be another model than the agent, since the fork's evaluator refuses self judging. The scripted agent and the baseline policies need no key.

## Glossary

Each row gives a term of the paper, the name that the code and the texts an agent reads give the same thing, and what it means. The pages give a key, a tool or a text that an agent reads under its name in the code.

| baseline policies | reference policies, `REFERENCE_POLICIES` in `CausalDiagnosis/experiments/table_definitions/experiment_tables.py`, `CausalDiagnosis/environment/reference_policies/policies.py` and `CausalDiagnosis/environment/reference_policies/greedy_policy.py`, the greedy reference for the greedy baseline policy | the policies that call no language model, the oracle policy and the greedy baseline policy among them |
