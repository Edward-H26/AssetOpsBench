# Hydraulic Rig Dataset

The environment replays an existing public dataset and generates none of the readings that an agent sees. Every reading is a recorded cycle of dataset 447 of the UCI Machine Learning Repository, the condition monitoring recordings of a hydraulic test rig. The episodes around the recordings are generated by deterministic rules with pre-registered seeds. The clock, the prices, the repairs, the deterioration and the failure rule are rules of the environment, and the section Assumptions lists what they assume beyond the recordings.

Each section states its rule for any asset and then gives the hydraulic rig as the worked instance. Every count on this page is recomputed from the code and the data by `CausalDiagnosis/datasets/hyd_1/tests/test_dataset_doc.py`, so a change of the data, the asset file or a seed that moves a count fails that test. No value on this page is the outcome of an experiment. The related pages are [environment.md](environment.md) for the rules of an episode, [metrics.md](metrics.md) for the measures, [experiments.md](experiments.md) for the evaluation scripts and the tables, and [adding-a-dataset.md](adding-a-dataset.md) for a further asset.

## Source

An asset is added to the environment as a data file of recorded cycles, each with the condition level of every component, and an asset file that specifies the components, their levels, the channels and the rules. A combination assigns one level to each component. The stable cycles recorded under one combination form the block of that combination. The environment provides recorded blocks only, so every combination that an episode can reach needs a block.

On the rig, the recordings are dataset 447 of the UCI Machine Learning Repository, Condition monitoring of hydraulic systems. The rig repeats a constant load cycle of 60 s and records 17 sensor channels and one row of condition labels per cycle. The labels set 4 components to known condition levels, the cooler, the valve, the pump and the accumulator, with 3, 4, 3 and 4 levels. All 144 combinations of the label grid have a block. The asset file `CausalDiagnosis/datasets/hyd_1/asset.json` contains these tables and the label keys under `records.label_keys`.

The environment reads the cycles from one data file, which one command fetches and builds from the UCI archive. `CausalDiagnosis/datasets/hyd_1/download_and_build.py` downloads the archive from the official page, refuses a file whose SHA-256 differs from the pinned one and builds the data file. The build is that of `CausalDiagnosis/datasets/hyd_1/build_features_and_blocks.py`, which computes the block of every combination and, for every cycle, the statistics that a reading returns. The table of data sources at the end of this page gives the command.

Two public copies of the same recordings are used as cross-checks. The IndustryAssetEQA facts file of the public EmbodiedQA repository contains the cycles with their labels, and `build_features_and_blocks.py` with `--cross-check` compares its own labels and statistics with that file for every cycle. The copy of the rig that AssetOpsBench ships, `src/couchdb/scenarios_data/shared/iot/hydraulic_pump_1.json`, contains the 17 channel means of the same cycles without labels. `CausalDiagnosis/datasets/hyd_1/verify_data_facts.py` checks that the data file and this copy agree on every channel mean of every cycle, and the environment takes its public field names from the AssetOpsBench copy.

On the configurations that run on the tools of AssetOpsBench, the documents that its servers read are written by the environment itself. `CausalDiagnosis/frameworks/AssetOpsBench/tool_servers/episode_documents.py` writes the registry, failure mode and telemetry documents of every episode from the asset profile through `CausalDiagnosis/frameworks/AssetOpsBench/tool_servers/profile_documents.py`. The environment reads no recordings of any other asset of AssetOpsBench.

The 17 anchored scenarios are the hydraulic pump records of the AssetOpsBench dataset on Hugging Face. `CausalDiagnosis/frameworks/AssetOpsBench/scenarios/download_scenarios.py` fetches them at a pinned revision and checks their SHA-256, and the repository contains no copy of them.

## Assumptions

Each assumption is a choice of the environment that the recordings cannot confirm. The rule applies to any asset, and the last column states what would break on the rig.

| Assumption | Code | What breaks if it fails |
| --- | --- | --- |
| The recorded condition labels are the true hidden state of a cycle. | `load_cycles` in `CausalDiagnosis/datasets/dataset_loader/recordings.py` reads them under `records.label_keys`, and the verifier scores against them | every score is measured against a wrong truth for the mislabeled cycles |
| The stable cycles of a combination stand for that combination at any time of an episode. | `RecordingSource.open` in `CausalDiagnosis/datasets/dataset_loader/evidence_source.py` provides the same block whenever the asset is in that combination | a rig whose readings drift within a combination over hours or days would look different from the replay |
| The cycles of an episode, repeated, stand for the rig running on in that combination. | `play` in `CausalDiagnosis/datasets/dataset_loader/evidence_source.py` wraps the cycles | an agent that reads more cycles of one combination than the episode contains sees exact repeats, which a running rig would not give |
| The recordings of a combination do not depend on the path that reached it. | `RecordingSource.open` provides the block of the state whatever the history, and a combination met again resumes where it stopped | transients after a repair or after a transition, and any hysteresis, are absent from the replay |
| A repair takes effect all at once, when its work order closes. | `close` in `CausalDiagnosis/environment/Causal_Diagnosis_Environment/layers/layer_4_repair_rules.py` calls `set_level` of the clock, which opens the block of the repaired combination | a gradual recovery or a partial repair would show readings that the replay never provides |
| A component moves one recorded level down at a time, by the schedule or at the rates of the asset file. | `draw_schedule`, `hazard_rate` and `drops` in `CausalDiagnosis/environment/Causal_Diagnosis_Environment/layers/layer_5_deterioration_and_failure.py` | the schedule and the rates are design parameters, so when and how often a transition occurs is a design choice and not a measurement |
| A component at its worst level fails after the time to failure of the failure rule, `patience`, unless a repair restores it by then. | `failure_check` in `CausalDiagnosis/environment/Causal_Diagnosis_Environment/layers/layer_5_deterioration_and_failure.py` | the dataset contains no failure, so the time to failure is a design choice |
| The 10 starting offsets of a combination are different views of one block. | `RecordingSource.starts` in `CausalDiagnosis/datasets/dataset_loader/evidence_source.py` gives every combination the same 10 offsets | episodes of one combination share their recordings, so they are not independent rigs |
| The asset of the anchored scenarios is the AssetOpsBench copy of the rig with one recorded cycle per day, and the hidden initial state of an anchored episode is the recorded condition of its day. | `ASSUMPTIONS` in `CausalDiagnosis/frameworks/AssetOpsBench/scenarios/scenario_anchors.py` | an anchored episode may not show the fault that its scenario text states, and the authors of AssetOpsBench have not confirmed either point |
| The prices, the action durations, the lead times, the repair downtimes, the production loss rates, the failure penalty, the budget, the horizon, and the step limit take the values that the environment declares. | `defaults` of the asset file (`prices`, `durations`, `limits`, `clock`) in `CausalDiagnosis/datasets/hyd_1/asset.json`, with the production loss rates in the card `downtime` and the failure penalty in the card `failure` of its `rules`, read by `AssetProfile` in `CausalDiagnosis/datasets/dataset_loader/profile_data.py` | every cost, every delay, and every comparison that depends on these values holds for the declared values alone |

## Episodes and splits

For any asset, the test combinations are the recorded combinations that the fault rule of its asset file allows. Every other recorded combination is a development combination, and a development episode starts in a faulty one. Every faulty level of every component must appear among the faulty development combinations. When one does not, the fewest test combinations that complete the coverage move from the test set to the development set under a pre-registered seed. `development_starts` and `starts_of_test_set` in `CausalDiagnosis/datasets/splits/development_split.py` compute the initial combinations of the two sets. An episode that starts in a development combination can reach the recordings of a test combination after a repair, as every repaired episode reaches the fault-free recordings. The split separates initial states and not recordings.

On the rig, the fault rule allows 1 to 2 faulty components in the initial state. Of the 144 recorded combinations, 47 are test combinations, 10 with one fault and 37 with two. A development episode starts in one of the 96 recorded combinations with 3 or 4 faults. Every faulty level of every component appears among them, so no test combination moves. The fault-free combination is a development combination as well. No development episode starts in it, and it is the initial combination of the false-alarm control alone. An initial state is a combination with a starting offset. Each test combination has 10 starting offsets, so the environment can draw 470 initial states of the test set, which `start_states` in `CausalDiagnosis/environment/Causal_Diagnosis_Environment/start_state_seeds.py` lists.

The test set consists of 5 replicates of every test combination, 235 episodes. The first replicate draws one seed per combination from the 8 smallest seeds that reach it, under the master seed 42. The smallest of the 8 is set aside, as `reserved_seeds` lists, and no test replicate and no training episode uses it. Each later replicate starts at an offset that no earlier replicate uses, drawn by `sampled_combination_seeds` in `CausalDiagnosis/environment/Causal_Diagnosis_Environment/start_state_seeds.py`. One label per initial combination states whether the greedy scripted policy identifies that combination, every level, within the budget in more than half of its rollouts. The label runs 10 rollouts on seeds after that pool, so no rollout of the label repeats an episode of the test set. The label depends on the initial combination and on the rules key of the configuration alone, its prices, durations, production loss rates, horizon, budget, fault rule, step cap, failure card, sensor groups, asset and clock. The scripted policy starts from a uniform prior over the combinations and reads no past work order, so the label is the same for every agent and does not change where a configuration provides the repair history.

The pre-registered evaluation adds a descriptive false-alarm control on the fault-free state. Each of the 6 agent configurations of the first experiment runs on the fault-free combination at 5 starting offsets, 30 episodes, under the configuration `healthy_control`. Every episode opens with the same sentence, that the performance monitor flagged the unit, and asks the same question. On the fault-free combination the alert is a false alarm of the monitor, and no agent can tell a control episode by its text. The control reports two counts per configuration, the false alarms of the agent and its unnecessary work orders. The control includes no test and belongs to no family. The fault-free combination is no test combination, and the normal range of every channel is the range of its own stable cycles. So no channel mean of a control episode lies outside its normal range, and the control counts only the false alarms that an agent raises without such a reading.

For any asset, training and evaluation are cross-fitted over K folds by the rule of `CausalDiagnosis/datasets/splits/train_test_folds.py`. The faults of the test combinations, each a component at one faulty level, are partitioned into K folds under a pre-registered seed. Each model holds out one fold. A model trains on the initial states that contain no fault of its held-out fold and from which no repair reaches one. The same model is evaluated on the test combinations assigned to that fold, each of which contains a fault of the fold. So every test combination is one that its model never trained on, with at least one fault that the model never trained on. The folds file of the asset lists every test combination with the fold whose model is evaluated on it and the models that train on it. `CausalDiagnosis/experiments/table_definitions/write_training_split.py` writes that file before any run, as step 6 of [adding-a-dataset.md](adding-a-dataset.md) describes.

On the rig, the folds file `CausalDiagnosis/configs/training/hyd_1/folds.json` partitions the 10 single faults into K = 2 folds from seed 0. The folds contain 24 and 23 test combinations. Each model trains on 14 combinations. Of the 37 combinations with two faults, 18 contain both faults in one fold and 19 contain one fault from each fold. The model that is evaluated on those 19 combinations, 95 test episodes, trained on one of their two faults alone and never on the pair. A model trains on the 5 initial states of each of its training combinations that no replicate uses, 70 per model, which `training_start_states` lists. A training episode repeats no rollout of the label and uses no seed that is set aside. A training episode may read the same recordings as a test episode, since a block provides only 10 cycles. Only a transition to a worse level, which the deterioration layer adds, can put a held-out fault into a training episode.

## What an agent is told and what ends an episode

For any asset, the environment provides no table that links a channel to a component and no reference of the value that a channel takes at a fault level, beyond what the documents of the asset state. On the rig, every model agent of the experiments uses the tools of AssetOpsBench. The asset profile returns the components, their levels, the sensor sets, the prices, the limits and the normal range of every channel mean. The failure mode tool returns the failure mode codes of a component class and no channel. The asset registry lists the channels under the asset and none under a component. An agent can read the link from the names of the channels, such as the channel of cooling efficiency and the component cooler. From the repair rules layer on, the repair manual lists the channels that indicate a component. The action server of the rig, through which the scripted policies act, returns the failure modes of a component with the channels that indicate it, as [environment-actions-mcp.md](environment-actions-mcp.md) describes. The initial combination, its recording indices and the rule that draws the initial states are never provided.

For any asset, an episode ends only on a condition that the task description or a tool description states. A call that the rules do not allow is refused, the refusal states its reason, and the episode goes on. On the rig, the task description lists every end condition. An episode ends on the finish call, at the horizon, at the step limit and at the wall-clock time limit. An episode also ends when an action would exceed the budget of a configuration with a budget, and on a failure where the failure rule is strict. A refused call is charged nothing and counts as a step.

## What the counts can detect

For any asset, every pre-registered comparison is paired. Two agents run the same test episodes, the difference of an outcome is taken per episode, and the episodes of one test combination form one cluster, since they share the recordings of that combination. The p value of every test comes from an exact permutation test that flips the signs of the cluster sums, and the interval comes from the cluster bootstrap, both in `CausalDiagnosis/evaluation/metrics/table_statistics.py`. Holm's step-down procedure controls the familywise error rate over the tests of one family at alpha = 0.05. The pre-registered analysis names three primary families. H0 tests the judge against the verifier, and H1 and H2 compare the agents on the base layer. The third primary family asks H1 again on the full environment and adds H2' there, and Holm's procedure corrects the tests of both hypotheses as one family. The other families of the table, the layer study and the training family, are secondary.

Two design computations bound what a family can detect. The exact permutation test over n clusters whose sum is not zero has its smallest two-sided p value at two to the power of one minus n. The first Holm step can reject only when n reaches the bound n_min below. The minimum detectable effect of a binary outcome, MDE below, follows a normal approximation at power 0.8. The approximation takes the proportion of discordant pairs, the share of episodes on which the two agents differ, and an effective number of units. The effective number lies between the number of clusters, when the replicates of a combination always agree, and the number of paired episodes, when the replicates are independent.

```
n_min = ceil(1 + log2(m / alpha))
MDE   = (z(1 - alpha / (2 m)) + z(0.8)) * sqrt(p_d / n_eff),   C <= n_eff <= C * r
```

In both formulas m is the number of tests in the family, C the number of clusters, r the number of paired episodes per cluster and p_d the proportion of discordant pairs.

On the rig, the test set has 47 clusters of 5 paired episodes, 10 combinations with one fault and 37 with two. A fault of the cooler stands in 18 test combinations, of the valve in 24, of the pump in 18 and of the accumulator in 24. Under the dependency rule of the repair rules layer, the order of the repairs matters in 12 of the 37 combinations with two faults, those with a faulty pump and a faulty valve or accumulator. The rule switches on with layer 4, so on the layers below it the order of the repairs never matters in the replay. A difference between two agents arises mainly on the test combinations that the label of the greedy scripted policy marks, so the power of a family rests on those combinations.

The table gives the instance of both computations, with the minimum detectable effect as the range from all paired episodes to the clusters alone. The numbers of the table are a design computation from the counts and no run. The columns of the minimum detectable effect apply to the binary outcomes of a family, Top-1 and pass, and not to the tests of normalized cost.

| Family | Tests | Clusters | Episodes per cluster | Smallest n | MDE at p_d 0.1 | MDE at p_d 0.2 | MDE at p_d 0.3 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| H1 and H2 on the base layer | 14 | 47 | 5 | 10 | 0.08 to 0.17 | 0.11 to 0.24 | 0.13 to 0.30 |
| H1 and H2' on the full environment | 14 | 47 | 5 | 10 | 0.08 to 0.17 | 0.11 to 0.24 | 0.13 to 0.30 |

No stratum is tested. A stratum has intervals beside the decision, and only the families over all 47 test combinations decide. The stratum of training on the combinations with one fault has only 10 clusters, below the 11 that its family needs, so it could not reject on its own in any case. The premise with the least support in these counts is that the interaction with the environment decides the scores and not what the model knows before it reads. Nothing in the counts shows that a model needs more than the first readings to identify a fault. Ablation Sc3 tests that premise with a static agent that answers in one model call from the first replayed cycle, against the 6 agent configurations under the base configuration.

## Limitations of the data

The rig is a test bench under a constant load cycle and not an asset in the field, and every fault was set by its experimenters. The condition levels are discrete settings of the bench, so degradation between two levels is never recorded and a transition jumps one level at once. No failure was recorded, so the failure rule, the deterioration rates, the prices, the durations and the production loss rates are design choices and not measurements.

The replay repeats exact values. A combination provides 10 stable cycles, and the 5 cycles of an episode repeat in the same order, so a long series of readings of one combination returns the same cycles again. The episodes of one combination share one block, so the 5 replicates of a combination are not independent rigs, and the evidence rests on the clusters and not on the episodes.

The normal range cannot raise a false alarm in the replay. The range of a channel is the smallest and the largest mean over the stable cycles of the fault-free block, and every cycle of that block that the replay provides is one of them. A range over the stable cycles of one block is narrower than the spread of the bench over a longer time, so a new fault-free cycle of the rig can fall outside it. Every check against the range reads the same range, for the agents and for the CausalDiagnosis MCP alike, so the effect on a comparison has no known sign.

For any asset recorded as one contiguous run per combination, a slow drift of the bench is confounded with the condition. On the rig the combinations were recorded in sequence, so part of what separates two neighboring combinations in the replay can be the time of their recording and not only their condition. The pre-registered runs do not control for the order of the recordings, and the replay provides the cycles as recorded.

The environment contains one recorded asset, so every general rule of this page has run on the recordings of the rig alone.

## What a further dataset would need

An asset of the kind `recorded_levels` needs recorded cycles with the condition level of every component per cycle. Every combination that an episode can reach needs a block of at least 10 stable cycles, which applies to the initial combinations, to every combination that a repair or a transition leads to and to the fault-free combination. The asset needs its failure modes with the channels that indicate them, and a license that allows a public rebuild of the data that the environment reads. The table checks the rig and the IndustryAssetEQA data of the public EmbodiedQA repository against these needs, and each IndustryAssetEQA cell states the file of that repository it rests on.

| Need | The rig, UCI dataset 447 | IndustryAssetEQA |
| --- | --- | --- |
| condition level of every component per cycle | yes | `data/outputs/hydraulic/hyd_facts.jsonl` contains the cycles of the rig with their labels, while `data/outputs/pdm/pdm_facts.jsonl` identifies one failed component per time window of the Azure predictive maintenance data and no condition level |
| stable recordings for every fault combination | yes | no for `data/outputs/pdm/pdm_facts.jsonl` and `data/outputs/cmapss/cmapss_fd001_facts.jsonl`, which record windows before failures and runs toward failure, not fixed combinations |
| failure modes and indicating channels | taken from published sources, the facts released with IndustryAssetEQA and the paper of the dataset, as the asset file states | `data/fmea_kg/FMEA_KG.ttl` covers subsea and offshore oil and gas equipment and lists no channel of the rig |
| license for a public rebuild | `CC BY 4.0` | the repository root has no license file |

A new asset is added as a data file and an asset file, as [adding-a-dataset.md](adding-a-dataset.md) describes. The fold rule of `CausalDiagnosis/datasets/splits/train_test_folds.py` and the initial states need nothing beyond the asset file, and `CausalDiagnosis/experiments/table_definitions/write_training_split.py` writes the split of the new asset before any run. Each assumption above has to be checked again for the new recordings. Two matter most, that the stable recordings of a combination stand for it at any time and that a repair takes effect by a switch to them. A dataset without labeled fault combinations does not fit the kind `recorded_levels` and is added through another evidence kind, which adding-a-dataset.md describes.

## Distribution and license

Every dataset is identified by its official page and by one command that fetches it and checks its SHA-256. The repository contains no dataset file and no file derived from single records, and git ignores its data folder except the checksum file. A run folder contains readings of single records and is no part of the repository. Of a run the repository publishes the aggregate tables.
