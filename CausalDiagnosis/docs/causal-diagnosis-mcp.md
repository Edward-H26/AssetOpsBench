# CausalDiagnosis MCP

`CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/` is the CausalDiagnosis MCP of the hydraulic rig gym, registered under the MCP name `causal_diagnosis`. It offers four read only tools over the evidence an episode has released: `get_episode_evidence` lists the readings with their normal ranges and anomaly scores, `rank_root_causes` ranks every combination of the asset profile as the condition of the rig now, by a belief that a filter carries over the released history under the public rule cards and updates with an interventional effect model, decides by the rule of the CausalDiagnosis MCP whether to read the record before a diagnosis and which read, with the advice that names the next step, ranks every read by its information gain per unit cost with its expected elimination and its one step edge cutting score reported beside it, reports in its long forms the earlier rule with the batch of reads whose order no outcome can change, and walks each top combination forward to a restored rig as a candidate plan, `estimate_intervention_effect` predicts what a repair would do with conformal intervals, and `verify_outcome` checks a stored prediction against the recordings after the repair. Every threshold in a result traces to a price, a duration, a downtime rate or the declared error level, and the assumptions of every result say how. The CausalDiagnosis MCP contains no language model and never opens the hidden state. Its launcher names the initial combination of the episode, whose recorded block every fit leaves out and which the CausalDiagnosis MCP uses for nothing else. This page covers the design rules, the asset view, the models file and the grade table, the contract of the tools, the four tools with their results, the filter, the formulas E1 to E22 with the module that implements each, the ranking models and the abstention rules, information gain and the read batch, the candidate plans, the calibration report, and how to run and test the CausalDiagnosis MCP.

Related docs: [README.md](README.md) for the index, [environment.md](environment.md) for the environment and its data file, [environment-actions-mcp.md](environment-actions-mcp.md) for the episode files, the released evidence and the tool contract, [experiments.md](experiments.md) for the drivers and the ablations, and [../mcp-servers.md](../../docs/mcp-servers.md) for every MCP server of the repository.

Names on this page follow the code and the texts that an agent reads, and the [glossary](README.md#glossary) of the docs README gives the term of the paper for each of them, such as sensor set for sensor group, rule for card, batch of reads for read batch and configuration for row.

## Design rules

- **Deterministic.** The same released evidence, stored predictions, models file and left out block give the same result. The Monte Carlo of the decision rule, of the information gain and the expected elimination, of the edge cut, of the read batch and of the grade is seeded with declared seeds, and no tool prompts a language model.
- **Only what the agent has seen.** The tools read `released.json`, which `write_released` of `CausalDiagnosis/mcp_servers/Environment_Actions_MCP/episode_state.py` rewrites after every call, through the metering layer on every row of the environment table and through the action server for the baseline policies, the gym and training, and the predictions the CausalDiagnosis MCP stored itself in `predictions.json` beside it. They never open the state file `episode.json`, the hidden files of an episode or the data file, so they never see the seed, the hidden combination, a recording index or a recording not yet served. The one hidden value that a process of the CausalDiagnosis MCP receives is the initial combination of its episode, which the launcher names so that every fit of the episode leaves the block of that combination out, and which the CausalDiagnosis MCP uses for nothing else. No result, note or file of the CausalDiagnosis MCP names it, and the notes of a result are one text whatever the initial combination. The view of the asset drops the fault rule of the initial states, the allowed initial combinations, the initial combination and the seed whatever a caller hands in, so no formula of the CausalDiagnosis MCP can read how the environment samples its initial states, and no assumption of a result names that rule.
- **One server per episode, no memory between calls.** A copy of the launcher beside `released.json` binds a process to one episode, so no tool takes an episode identifier. Every call replays the released evidence from cycle 0 through the filter, so a process started for each tool call, as the Plan-Execute executor does, answers exactly as a long lived one would. The models file is parsed and the fits of the episode are built once per process.
- **One view of the asset.** `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/asset_view.py` is the only module of the package that reads the tables of an asset, through `profile_view(rules)`, and a test fails when another module imports one. [The asset view](#the-asset-view) gives its content.
- **No fit reads the block of the initial combination.** `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/offline/fit_models.py` writes once the stable cycles of every recorded combination and the form of the model for each of them, and at launch the CausalDiagnosis MCP builds the fits of its episode from them. Every candidate root cause is scored by a fit that leaves out two recorded blocks, that of the initial combination and its own, or that of the initial combination and one second block where it has no block of its own among the others, for its mean, its within covariance and its block covariance. The same file serves every episode, so it carries no information about the hidden combination of an episode. [The models file](#the-models-file) gives the reasoning.
- **Every threshold traces to a cost or to alpha.** The rule of the CausalDiagnosis MCP reads the record once before a diagnosis, where readings have prices the read that the budget pays beside the repair of every component, and the earlier rule of the long forms compares expected losses built from the released prices, the price of a wrong diagnosis among them, durations and downtime rates. The information gain that ranks the reads divides by a read cost that exists on every row of the environment table, and the floor `IG_EPSILON` that a read batch requires of it guards against rounding and is not a decision threshold. The intervals and the verdicts use the declared error level `alpha`. No fixed confidence cut enters a default result, and the one cut the CausalDiagnosis MCP knows is an ablation arm named in the result that uses it.
- **A bounded call.** The work of one call is fixed by the released evidence. The filter merges equal states, and it carries the resampled fits of E6 only while the number of states times the number of fits stays within `RESAMPLE_WORK` of `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/belief/belief_filter/`. Every ranking reports its number of augmented states and of resampled fits in its fields, and the details `summary` and `full` state them with the bound in their assumptions. The tests hold the work of one ranking after many cycles under the heaviest rule cards within that bound and print its seconds to the log of the test, since a wall clock reads the load of the machine and not the code. Every ranking writes its wall time to the log of the CausalDiagnosis MCP on stderr, the logger `CausalDiagnosis.mcp_servers.Causal_Diagnosis_MCP.timing`, which the log of a job records. A call moves no clock itself. Where the clock of an episode counts the seconds between two calls of the environment, through the action server or the metering layer, the seconds of a call to the CausalDiagnosis MCP lie between two such calls and count as thinking time, the seconds in which a process of the CausalDiagnosis MCP builds the fits of its episode included.
- **Read only.** Every tool is registered with `readOnlyHint` true, since none changes the asset or the case record. `estimate_intervention_effect` and the candidate plans of `rank_root_causes` store their predictions in `predictions.json`, the record of the CausalDiagnosis MCP itself, which is the only file the tools write, beside the empty lock file `predictions.json.lock` that every store holds while it reads the file, numbers its record and writes it back, so that two processes of the CausalDiagnosis MCP in one episode that store at once write both records under two identifiers and share one record of a candidate plan. The process of the CausalDiagnosis MCP also appends every tool listing and every answer to `transcript.jsonl`, the transcript that the servers of an episode write, with the text of the answer and the SHA-256 of the released evidence that the call read, as [experiments.md](experiments.md) describes.

`CausalTools` in `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/tools/causal_tools.py` implements the tools as plain methods, testable without the mcp package, and `build_server` in `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/main.py` registers them with FastMCP. The diagnostics of the tools go through `EffectDiagnostics`, the implementation of the `DiagnosticsModel` protocol in `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/belief/diagnostics_model.py`: `hypotheses`, `prior`, `predict`, `update`, `tests`, `expected_elimination`, `information_gain`, `after_repair`, `repair_plan` and `outcome_check`, with `replay` for the belief now. The adapter binds the model through `diagnostics_backend`, which refuses a backend that lacks a member of the protocol and names the member.

## The asset view

`profile_view(rules)` returns the `ProfileView` the CausalDiagnosis MCP reasons over: the components in the order of every combination tuple, their levels, healthy levels and degradation order from healthy to worst, the grid of every combination, the sensor groups with their channel fields, the summary fields (the mean and the standard deviation of every channel), the public rules of the episode (prices, durations, downtime rates, budget, horizon, step cap, clock mode and normal ranges), and the parameters of the rule cards in `processes`: the schedule, the stochastic hazard, the emergency option, the dependencies, the priorities, the history rule and the failure card. `processes_source` records for each card whether its parameters came from the `processes` block of the released rules or from the default configuration of the asset profile, and every ranking names the cards read from the defaults in its assumptions. The function builds the view from the asset profile that `get_profile` of `CausalDiagnosis/datasets/dataset_loader/profile_registry.py` returns for the released `asset_id`, `hyd_1` when none is released, with the profile's default configuration for the rules and cards the release leaves out, and it refuses released components, levels or healthy levels that are not the profile's own.

## The models file

`models.json` in `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/` is generated from the rig data by `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/offline/fit_models.py`. `ensure_models` fits it when it is missing or in another format, and refuses a file fitted on another data file than the one in use, which it never refits in place. The drivers call it before they start a server or look a grade up. `load_models` parses the file once per process into a `Models` object (the space of the asset, the stable cycles of every recorded combination with their means, lengths and sums of centered products, the folds and the form of the model of every initial combination) and raises `FileNotFoundError` with the fit command when the file is missing, so the CausalDiagnosis MCP cannot start without it. `Models.without(start)` builds the fits of an episode that started in `start`, once at launch. To refit from the fork root:

```bash
PATH=$PWD/.venv/bin:$PATH PYTHONPATH=src python -m CausalDiagnosis mcp_servers fit-models [--asset-id ID] [--resamples N] [--seed S] [--out PATH]
```

**The fits of an episode.** Every combination has one recorded block, and an episode serves the recordings of the block of its initial combination, so a fit that read that block would recognize the readings it scores. Each candidate root cause h is scored by a fit that leaves out two recorded blocks. For a candidate root cause with a block of its own among the others, the two are the block of the initial combination and h's own, so that its mean is the prediction of h by that fit, its within covariance pools the cycles of the same blocks, and its block covariance is the covariance of the leave one block out misfits among them. A candidate root cause without a block of its own among the others, the initial combination itself and any combination without a recording, is scored by the fit without the block of the initial combination and one second block, which a hash of the levels of the initial combination picks among the recorded combinations one component away from it, or among all the others when none is recorded (`second_block`), so the choice depends on no order and on no process. A near rival of the initial combination, one component away, is scored by a fit without the block of the initial combination, which is one of its neighbors, so the fit that scores the initial combination itself leaves out a neighbor of it as well. No fit reads the block of the initial combination, and every candidate root cause, the true one included, is predicted from the same number of blocks, none of them its own. `fit_episode` in `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/effect_model/recorded_blocks.py` and `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/effect_model/episode_fit.py` computes these fits from one weighted fit on the blocks without that of the initial combination, by the deletion formulas of one and of two blocks, and refuses a model in which one block or a pair of blocks alone identifies a term (`LEVERAGE_GUARD`), since a fit without them would not exist. `fit_episode` also refuses, by name, a pool whose design leaves a term that no recorded block identifies, and a summary that takes one value within every block of a fit, which then has no within variance, decided on the recorded values and not on a computed variance. The healthy reference of E3, the coefficients of E4 and the resampled tables of E6 follow the same rule. The driver reads the initial combination from the episode and names it in the launcher (`left_out=<levels>`), since `released.json` never holds it, and the CausalDiagnosis MCP uses it for the blocks its fits leave out, for the form of the model that `models.json` holds for it, and for nothing else. Without it every tool answers with the error `this server was launched without the block its fits leave out`.

**The form of the model.** The form is chosen before any episode and written into `models.json`. The development blocks are the recorded combinations outside the test set of the asset, by the one split of the environment (`development_blocks` in `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/asset_view.py`). A part of the form that the development blocks identify is chosen on them, for an initial combination among them on the others. A part that the development blocks do not identify is chosen once per initial combination, on every recorded block but the two that the fit that scores the initial combination itself leaves out, that of the initial combination and its second block, so the choice reads no block that this fit leaves out. The covariance estimator of one cycle is always chosen on the development blocks, among three registered estimators (`COVARIANCE_ESTIMATORS`), the pooled within covariance shrunk toward its diagonal, its diagonal alone, and the window width times the within block covariance of the means of consecutive windows of cycles, shrunk the same way. The chosen estimator has the largest held out density of the window means of a block around their own mean, in the stratified folds of the development blocks (`stratified_folds` of `CausalDiagnosis/environment/reference_policies/tier_classifiers.py`, through `folds_of`). A tie goes to the earlier registered estimator, and the first registered one is taken when the held out windows give fewer degrees of freedom than there are summary fields or when no estimator can be evaluated. The interaction pairs are selected forward by the cross fitted log likelihood of the cycles. The pairs are chosen on the development blocks when every pool of them that the rule uses identifies every pair in every training fold (`development_identifies`), and once per initial combination otherwise. On the rig the development blocks are the healthy block and the blocks of three or four faults, which identify the main effects and not every pair, so the pairs of the rig are chosen once per initial combination. The block effect is the registered ranking model, and the held out density of the window means with and without the offset of a block is reported and chooses nothing. `models.json` records where each part was chosen and which blocks each choice left out. The conformal calibration of E14, E16 and E17 scores the cycles of every block without that of the initial combination against the fit without that block, once per initial combination.

**Repairs.** The blocks that leave the fits are named at launch. A repair moves the rig to a combination whose block the fit of every other candidate root cause has read, the fit of the initial combination excepted when that block is its second block, so the readings after a repair, which the recovery check reads, are not scored as cleanly as the readings before it.

**The resampled tables of E6.** A resampled table draws the blocks without that of the initial combination with replacement and predicts every combination by the fit on the drawn blocks other than that combination's own copies, or other than the copies of the second block for a combination without a block of its own among the others, the rule of the means, so the initial combination, which no draw holds, carries no wider spread than any other combination (`test_the_widest_resampling_spread_names_the_start_no_more_often_than_chance`). Every row stands at its combination's place in the grid, also on an asset with a combination that has no recording. A draw that cannot identify the model without one of its drawn blocks is drawn again, at most `RESAMPLE_ATTEMPTS` times, in one order from the resample seed, and the CausalDiagnosis MCP draws a table when a ranking first asks for it.

**Cycles within a block.** The belief treats the cycles of one block as draws around the model mean that share one offset of the block and vary around it by the within covariance. Recordings can drift inside a block, and a covariance estimated from single cycles then misstates how far the mean of a window of cycles moves. The window estimator takes the window width times the within block covariance of the means of consecutive windows, each as wide as the live window that the environment serves. For independent cycles that product equals the covariance of one cycle, and the product grows with any drift inside a block that a window does not average out. The development blocks decide by the held out density of window means whether the form takes the window estimator. The level of E14, E16 and E17 does not rest on independent cycles, since the calibration gives every block one unit of weight.

`models.json`, format 8, holds:

| Field | Content |
| --- | --- |
| `format`, `generated`, `facts_sha256`, `records` | the format, the fit date, the SHA-256 of the data file and its number of records |
| `fit` | the rule in words, the numbers of fitted combinations and cycles, the number of folds and the fold seed, and the resample count and seed of E6 |
| `space` | the components, levels, healthy levels, summary fields and sensor groups of the asset view |
| `ranking_models`, `default_ranking_model` | the three ranking models and the default, `joint_block` |
| `folds` | the fold of every recorded combination in the stratified folds of the environment's classifiers |
| `blocks` | the stable cycles of every recorded combination, the summaries of each cycle |
| `form` | the rule in words, the window width, the registered covariance estimators and block effects, the development blocks, `parts` with where each part of the form was chosen, and the SHA-256 of the chosen forms |
| `selections` | per recorded combination, the form of its model, which holds the interaction pairs with the selection log and the blocks their selection left out in `left_out`, the covariance estimator with the criterion of every registered one, the fallback flag, the held out degrees of freedom and the block it left out in `covariance_left_out`, and the report of the block effects with the pairs it was computed under in `report_pairs` |

`test_models_json_holds_the_blocks_the_folds_and_the_form_of_each_recorded_combination_in_format_8` checks the file against the data file and computes the form of three initial combinations again by the rule.

**The grade table.** `grades.json` beside `models.json`, format 9, holds one table of diagnosability grades per hash of the released sensor groups, prices, durations, downtime rates, horizon, budget, whether a clock runs and the text of the grading rule (`rules_key` in `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/offline/diagnosability_grade.py`), so a table graded under another rule is never read, and neither the fault rule of the initial states nor the ranking model enters the key. The file names the SHA-256 of the data file that its models were fitted on under `facts_sha256`, and a file graded on another data file is refused. `ensure_grades(models, rules, budget=None, ranking_model=None)` returns the table, which grades a combination the first time it is asked for it, with a generator seeded by the combination's place in the grid, and writes the grade to the file at once under a lock on the file, so the entries do not depend on the order of the requests, two processes that grade at once keep both grades, and a later process reads them instead of computing them again. A combination is graded under the fits of an episode that started in it, which leave its block out as the CausalDiagnosis MCP of that episode does. `CausalDiagnosis/experiments/cluster_runs/precompute_grid_tables.py` grades every combination of every rules key of a grid before its lines start. `ranking_model` is accepted for the drivers' call and enters nothing. `grade_of(start, models, rules, ...)` returns the grade of one combination, or None when no rollout commits to it under the budget. The drivers nest this grade, with the binary label that `separable` gives it, beside the independent diagnosability label of the environment, which the verifier reads. Every recorded combination of the default rules is graded with

```bash
PATH=$PWD/.venv/bin:$PATH PYTHONPATH=src python -m CausalDiagnosis mcp_servers diagnosability-grade [--asset-id ID] [--models PATH] [--budget B] [--rollouts R] [--samples N] [--seed S] [--force] [--out PATH]
```

Both files are git ignored. A rollout commits as soon as it has read the record before cycle 0 wherever it reads no live window, and on a row that prices nothing and has a clock a rollout that never commits to the true combination reads on until no read is left within the budget, so there the first request of a grade can take a while. A registered asset other than `hyd_1` is fitted, graded and reported with `--asset-id`, on the data file that its profile names. Each of the fit, grade and calibration commands then refuses its default paths, which serve `hyd_1`, so `--out` names the asset's own models file, grades file or report folder, `--models` names the models file that the grade and the report read, and `build_server` serves that models file through `models_path`.

## Contract shared by the tools

**Inputs.** The tools check the `format` of `released.json` against `RELEASED_FORMAT` and read its `rules` (the sensor groups, the prices, the durations, the downtime rates, the budget, the horizon, the step cap, the clock mode, the normal ranges and the `processes` block of the rule cards when present), its `status` (`time`, `budget_left`, `steps_left`, `open_work_orders` with the cycle at which each will close, `episode_over`), its `observations` (the readings with `n`, `t`, `sensor_group` and `values`, each stamped with the cycle it was recorded in), its `read` events (`t_end` and the readings each served), which tell a reading served while the clock stood at its cycle from one recorded during a cycle the clock ran, its `work_order_created` events (for the mode of an order, standard or emergency), its `work_order_closed` events (`id`, `component`, `source`, `t_end`), which enter the filter as closures after the readings released before them, its `refused` events, which `verify_outcome` reads for a refused work order, and its `fix_history` event when the agent has asked for the history. Without a released file, with a server started without an episode or launched without the block its fits leave out, every tool answers an error.

**Parameters.** Every parameter is flat and typed, and required except `branch_detail` of `rank_root_causes`, a view option of three values, `compact`, `summary` and `full`, with the default `compact`, because the Plan-Execute argument filler sees only the name, the JSON type and the required flag of a parameter and a caller that does not know the option should get the compact reply. The tool descriptions state the legal values and carry no number. The entries of the CausalDiagnosis MCP in `CausalDiagnosis/environment/Causal_Diagnosis_Environment/tool_contract.json` list the tools and their parameters.

**Results.** Each tool returns a pydantic model of `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/tool_result_schemas.py` that extends `ToolResult`, or an `ErrorResult` whose field `error` explains a bad argument or a missing episode. A client receives the error as an ordinary answer, `{"error": ...}`.

| Field | Content |
| --- | --- |
| `evidence_ids` | `obs/{n}/{field}` for a released value, `wo/{id}` for a closed work order, and `pred/{n}` for a stored prediction, the identifiers the result rests on, with `pred/b{n}` for a prediction stored by a candidate plan |
| `time_window` | `start`, `end` and `unit`, which is `cycle`: the first reading used and the current time, or for a prediction the current time and the time the action would end |
| `assumptions` | plain statements of the formulas behind the answer, each threshold traced to its price, duration, downtime rate or alpha, with the Monte Carlo count and seed where one is used, and for a ranking the number of augmented states and of resampled fits, while the compact reply of a ranking holds one text that names what it leaves out |
| `uncertainty` | `kind`, `value` and an optional `detail` |
| `message` | a one line summary, which the audit report prints |

| Tool | Uncertainty kind |
| --- | --- |
| `get_episode_evidence` | `largest_anomaly_score` |
| `rank_root_causes` | `top_marginal_resampling_interval`, with the interval and the top share in `detail` |
| `estimate_intervention_effect` | `recovery_probability`, with its resampling interval in `detail` |
| `verify_outcome` | `conformal_p_value`, the p value of the combined score |

## The filter

`Filter` in `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/belief/belief_filter/belief_filter.py` replays the released evidence into the belief at the current cycle, and `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/belief/belief_at_one_cycle.py` is its view over the combinations.

**The states.** The candidate root causes are every combination of the profile, 144 for the rig. The filter tracks augmented states x = (h, e, m), with h the combination now, e the point of the replay at which the recorded block of h was entered, counted in the recorded cycles observed before it, which fixes the readings that share the latent block offset of the `joint_block` likelihood, and m the rule memory, which holds the draw of the scheduled degradation rule (each scheduled component, its first drop cycle and its level at the start of the episode) and, for a component under an emergency hold, the level it returns to and the cycle of expiry. States with equal (h, e, m) carry equal Kalman states and are merged, so the number of states stays near the number of reachable states.

**The prior.** The prior is uniform over every combination of the profile, times the likelihood of the released maintenance history under the public history rule once the agent has asked for the history, times the probability of each draw of the schedule rule. The history rule gives every component one entry or none, an entry closed a number of cycles before the start of the episode that is uniform in the window of the component's kind, healthy or degraded, with the probability of that kind. The schedule rule draws the components healthy at the start of the episode first, uniformly, then the faulty ones, each with a first drop uniform in its window, as the clock's `draw_schedule` does.

**The predict step.** For every cycle the clock ran, the kernels of the active rule cards run in the order of `RigClock.advance_cycle`: the closures stamped with the cycle whose repair had a downtime, which closed at the end of the cycle before, the expiry of the emergency holds, the scheduled drops or the drops of the stochastic hazard, and the closures of repairs without a downtime, the closures of one cycle in the priority order in which the clock closes them, so that a dependency closing in the same cycle takes first. A closure takes only when every component its component depends on is healthy, else the order is ineffective and the state stays. An emergency close holds the level it replaced until its expiry and a standard close ends a hold. Replacing a healthy component damages it with the collateral probability of the hazard card. A scheduled drop sets an absolute level below the initial level, and the hazard drops every component below its worst level by one level with the rate of its depth. A kernel that changes h restarts the block offset at the model mean, so a combination entered twice starts a fresh offset.

**The update step.** The readings update the weights by the likelihood of the fits of the episode, every candidate root cause with its own mean, within covariance and block covariance ([The models file](#the-models-file)), so a reading before cycle 0 and a live one share the block offset of the block they were both recorded in. Every released reading enters once, where the rig served it. Readings of negative cycles, recorded before the episode began, update the prior before any cycle runs. Within a cycle up to the current one, the closures that ended the cycle before come first, then what the rig served while the clock stood at the cycle in the order it released them, the readings of a read of zero duration and, on a row without a clock or at a finish, the work orders that closed there, then the predict step of the cycle's other kernels, then the readings that a read taking cycles recorded during the cycle. A cycle served twice, because the recording window wrapped or two groups read the same cycle, enters once with the union of its summaries, where its first reading entered. Under `joint_block` the offset of the block is integrated out by a Kalman step per reading, under `joint` every reading is an independent Gaussian draw around the model mean.

**The belief.** `Filter.posterior` collapses the states to a `Posterior` over the combinations now: the mass of every combination, the mean of its block offset and its covariance, the moment matched mixture of its states when they differ, each state weighed by its share of the combination's own mass. The shares come from the log weights of the states, so the moments do not depend on the mass of the combination, also when a float holds that mass with a few bits only, below the smallest normal number. The predictive of a reading is factored once per combination with mass, in one batch. `Filter.ahead(cycles, plan)` runs the predict step forward on a copy, with the open work orders closing on their released cycles and the closures of a plan, and `Filter.next_reading` gives the copy at the belief that the next reading of one cycle meets, `ahead(1)` where a read takes cycles and the belief now where a read takes none. The resampled mean tables of E6 travel as extra rows of the weights through the same steps. The filter refuses by name a support that holds no combination of the asset, a schedule card that draws more components than the asset has, and readings that have zero likelihood under every state of a fit, and a belief refuses masses that sum to zero, cases that no row of the rig meets and a port of another asset can.

**E1, the interventional effect model.** The experimenters of the dataset set every component level, so the recordings under a combination are draws from the interventional distribution of the channel summaries under that combination, and the effect of a component condition on a channel is estimated from the recordings without causal discovery. The mean of each of the 34 summaries, the mean and the standard deviation of the 17 channels over one recorded cycle, is an intercept plus one main effect per non healthy level of each component plus the pairwise interaction indicators selected forward by the log likelihood of the combinations that a cross fit holds out. The selection of the form of an initial combination reads the blocks that the rule of the form names for it, on the rig every recorded block but that of the initial combination and its second block, so it reads the block of every rival of the initial combination and never the two blocks that the fit that scores the initial combination itself leaves out ([The models file](#the-models-file)). A pair is admissible only when the design keeps full column rank, a pair that some training fold cannot identify is not selectable, and `models.json` stores the selection log. The fit is weighted least squares on block means with the block lengths as weights, which equals least squares over cycles, and every candidate root cause is scored by a fit that leaves out two blocks, that of the initial combination and its own or the second block. Its within covariance is the covariance of one cycle of the same blocks under the covariance estimator of the form of the initial combination. The first registered estimator is the pooled within combination covariance, every block centered on its own mean, shrunk toward its diagonal. The shrinkage weight is a ratio clipped to the range from 0 to 1. Its numerator sums, over the off diagonal entries, an estimate of the sampling variance of the entry, computed from the products of the pooled deviations as if those deviations were independent rows. Its denominator sums the squares of the same entries. The ratio has the form that Schaefer and Strimmer give for a diagonal target, and it is not their weight for pooled deviations, since deviations pooled within blocks lose one degree of freedom per block, which makes the weight of the code smaller than a weight whose variance is taken over blocks, the more so the fewer rows a block holds. The second estimator is the diagonal alone, and the third applies the same shrinkage to the within block covariance of window means, times the window width. Its block covariance is the same shrinkage, or the diagonal under the second estimator, of the leave one block out misfits of the same blocks, how far the mean of a block lies from the prediction of a fit that did not read it. The resampled mean tables of E6 refit the model on block bootstrap draws of the blocks without that of the initial combination, every row predicted without its own block's draws or without the draws of the second block.

**E2, the belief.** The prior, the predict step and the update step of [The filter](#the-filter), over every combination of the profile. The default ranking model, `joint_block`, carries the latent block mean: the cycles of one recorded block share an offset from the model mean, since the block was recorded in one run of the rig under one setting and no fit of the episode read it. The offset has the block covariance of the fit that scores the candidate root cause, is integrated out by a Kalman step per reading, and makes repeated readings of one block add less than independent draws would, the same reason for which E6 resamples by block. The literal E2, the ranking model `joint`, leaves the offset out.

**E3, the anomaly score** of a summary is its absolute deviation from the clean prediction of the healthy combination, the mean of the fit that scores that combination, over the within standard deviation of the same fit. It enters no decision.

**E4, the attribution.** The predicted deviation of a summary under the top combination splits into the main effects of its faulty components and halves of their interactions, from the coefficients of the fit that scores that combination, the shares are normalized per summary, and a component's explained anomaly is the sum over summaries of the anomaly score times its share, for the top combination over the readings of the block that the heaviest state of that combination has been in since it was entered.

**E5, the marginals.** The fault probability of every component now and its level probabilities now, summed over the belief. Combinations are ordered by decreasing mass.

**E6, the stability.** The filter is replayed under the resampled mean tables of E1, as many as the work bound of the design rules allows, which the result reports as `resampled_fits`. The interval of the top component's marginal is its range over those fits, and `top_share` is the share of fits in which that component stays on top. No band constant is used. The same fits move through the predict step of a repair and give the resampling interval of the predicted probability of recovery of E13, a range over the `resampled_fits` fits of the call. The range of R fits holds a further fit with a probability equal to the ratio of R minus 1 to R plus 1, so it stands for the declared level only when R times alpha is at least 2 minus alpha, the bound that `fits_for_level` of `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/advice/conformal_intervals.py` computes, and E15 takes its dead band from it only then.

**E7, the costs**, from the released rules at the current cycle, in the unit of the episode's row of the environment table, which `cost_unit` in `CausalDiagnosis/environment/Causal_Diagnosis_Environment/layers/layer_1_priced.py` reads from the prices and the result names in `costs.unit`. From the priced row on the unit is money. An unnecessary replacement costs the part plus the repair charge plus the stopped downtime rate over the repair downtime. A missed fault costs its downtime rate over the remaining horizon. A test costs its read price for one cycle plus its declared read duration times the expected downtime rate of the belief now. On a row that reads a record a read moves no clock, so its duration is zero, it costs its price alone, and its reading meets the belief now. A wrong diagnosis, a combination off the truth in any level, costs `prices.misdiagnosis` of the released rules, zero when the rules do not carry it. On the free base row, where the rules price nothing, every cost of E7 to E10, E18, E21 and E22 counts tool calls. A read takes one call, the work orders of a candidate plan one call per order, and no downtime is charged. A diagnosis off the truth in any level, an unnecessary work order and a missed fault each void the pass, so each is charged the calls left before the step cap, the counterpart of the remaining horizon in money and what a failed episode spends, once. The step cap stands in for the budget that the base row does not have.

**E8 and E9, the two expected losses.** Acting on combination a repairs its faulty set and diagnoses a. When h is true its loss sums, over components, an unnecessary replacement where a is faulty and h healthy and a missed fault where a is healthy and h faulty, the repair loss, and adds the price of a wrong diagnosis when a differs from h in any level, since the score counts every level. On a row whose rules price nothing the loss is the calls left wherever a differs from h, once, since one error voids the pass as surely as several, so the best act is the most probable combination. E8 is the expected loss of acting on the top combination, the expected repair loss of its faulty set plus that price times one minus the top mass. E9 is the expected loss of first reading one cycle of a sensor group and then acting on the top combination of the updated belief, integrated by Monte Carlo with the declared sample count and seed over the predictive of the next reading, plus the test cost. Its predictive is drawn from the belief that the reading meets, one predict step ahead on the rows where a read takes cycles and the belief now on the rows where a read takes no simulated time, the rows of the first experiment among them, with the open work orders of a row without a clock closed first, since they close before the next call that is not an order. The standard error of the Monte Carlo mean is reported per test.

**E10, the decision of the earlier rule**, which the block `e10_rule` of the details `summary` and `full` reports for the read and repair choice ablations of the agent, while the rule of the CausalDiagnosis MCP stands at the top level of every detail, as [Ranking root causes](#ranking-root-causes) states. Under E10 `read_first` is true when some test lowers the expected loss below acting now, over the groups the row can still serve. The separating test is the test that lowers it most, and the expected saving is the difference. The candidate tests are one cycle of each sensor group. This is the one step rule of Heckerman, Breese and Rommelse written for the rig's prices, durations and downtime rates and for more than one fault. Since a wrong level costs the price of a wrong diagnosis, a test that separates two combinations of one faulty set can lower the expected loss. On such a split, for a read that resolves the top combination, the rule reads while one minus the top mass exceeds the test cost over that price, the priced form of E11, and with the price at zero, as on the free base row, a test counts only through the repair loss. The launch option `e10_margin` of the CausalDiagnosis MCP, zero by default, asks the best test to lower the expected loss by more than the margin times its cost. The flag of `e10_rule` is `read_first`, and its separating test is that test for one cycle.

**E11, the one component case.** With one uncertain component, one resolving test and a replacement that is unnecessary with probability one minus p, acting now is cheaper than testing when p is at least one minus the test cost over the cost of an unnecessary replacement plus the price of a wrong diagnosis, C_d of E7. It shows what a fixed confidence cut stands for.

**E12, the unseparated components.** A component is unseparated when the decision to replace it differs between the top two combinations and some test lowers the expected loss of that decision alone. Its separating channels are the fields of that test. Its loss is the repair loss alone, so a component whose level alone differs between the top two is not listed.

**E13, the belief after a repair.** The prediction is for standard orders, and no emergency order is predicted. The predict step runs from now through the cycles of one visit created now, with the closures of the repaired components on the cycles that `visit_schedule` gives, the open work orders closing on their released cycles, and the rule cards acting meanwhile, so a repair whose dependency stays degraded predicts no recovery. The probability that the action addresses a fault is the mass of the combinations now in which the component is faulty, and the predicted probability of recovery is the mass of the healthy combination at the first reading after the last close. `monitor` is one cycle without a repair: it addresses nothing, costs no price, lasts one cycle of waiting and accrues the expected downtime of that cycle, since no observation is free.

**E14, the conformal interval.** The predicted mean of a summary after the action is the mean of the most probable combination of the belief after it, from the fit that scores that combination, a tie going to the combination that comes first in the order of the candidate root causes. The interval is the leave one block out conformal interval, the mean plus or minus q times the within standard deviation of the summary, where q is the smallest calibration score such that at least (1 minus alpha)(n plus 1) units of calibration weight lie at or below it, n the number of blocks without that of the initial combination. The calibration set holds the cycles of every block without that of the initial combination, each scored against the mean of the fit without that block, with one unit of weight per block shared by the block's cycles, so that the exchangeability behind the guarantee is across blocks rather than across the correlated cycles of one block. The promise is a rate over the calibration blocks. For a block drawn at random among them and a cycle drawn at random in it, a summary lies in its interval at a rate of at least 1 minus alpha. Nothing is promised for one named combination. The level is reachable when (1 minus alpha)(n plus 1) is at most n. Below that the largest score stands in, no interval carries its level, and the results say so with `level_reachable` false (`Calibration.level_reachable`). `alpha` is the one declared constant, printed in every result.

**E15, risk and direction.** The risk before the action is one minus the mass of the healthy combination now, the risk after, a prediction, is one minus the predicted probability of recovery, and the direction is `lower`, `higher` or `no change` with a dead band equal to the half width of the resampling interval of the predicted probability of recovery, or `undetermined` when that interval is a range over fewer fits than the declared level needs, as E6 states, `dead_band` then null while both ends and `resampled_fits` are reported.

**E16 and E17, the verification.** On the first reading released after the closure of the component's work order and recorded at or after its cycle, every predicted summary the reading holds has a standardized deviation, the absolute residual over the within standard deviation, and the reading has one combined score, the largest of them over the summaries it holds. Its p value is one plus the weight of the calibration cycles whose combined score over the same summaries is at or above it, over n plus 1, n the calibration blocks, and the outcome is inconsistent when that p value is at or below alpha, one test per reading with no correction over summaries. A per summary p value cannot fall below one over n plus 1, which on this rig lies above alpha over the number of summaries that a reading of any tier holds, so a Bonferroni rule could never reject. The check scores the reading against the most probable combination after the repair, as E14 predicts it. What the leave one block out calibration promises is a rate over the calibration blocks. For a block drawn at random among them and a cycle drawn at random in it, the verdict finds the reading inconsistent at a rate of at most alpha when the level is reachable, at most alpha (n plus 1) minus 1 units of calibration weight, which `test_the_verdict_finds_at_most_its_exact_bound_of_the_calibration_weight_inconsistent` checks on the episode of a development combination. Nothing is promised for one named combination, and a reading of the block the episode started in, which a monitor prediction scores, is scored by a fit that holds one block more than the fits of the calibration. How often the check rejects a reading of another combination is not a claim of this page, and the one rejection test of the CausalDiagnosis MCP names its component, the cooler. The recovery check compares the predicted probability of recovery and its resampling interval with the mass of the healthy combination in the belief of the filter now, which holds every released reading and closure, the readings before the repair included, and which a ranking on the same evidence reports.

**E18, the grade**, the second diagnosability label. The grade asks whether the rule of the CausalDiagnosis MCP, played on the recordings that a row serves of the true combination, commits to it, every level, as pass scores it, in expectation over rollouts. A rollout starts from the static belief, a uniform prior over every combination of the profile updated by the `joint_block` likelihood, which is the filter when no rule card fires before the diagnosis, under the fits of an episode that started in the combination, which leave its block out as the CausalDiagnosis MCP of that episode does. The rollout reads the recordings before cycle 0 of a drawn entry offset without charge, as the rule of the CausalDiagnosis MCP and the independent label read them. On a row whose rules price nothing it reads every summary, and on a row with prices the reads of the record that the budget pays beside the repair of every component, the group that can still show the most summaries first, with only the prices counted against the budget, as the environment's budget counter counts them. Wherever no clock runs, and on every row with prices, the rule then diagnoses the most probable combination, so the rollout commits at once and the grade is binary, an entry whose cost and readings are zero. On a row that prices nothing and has a clock the rollout goes on over the live window of the same entry offset in play order, as the environment serves it, and reads the sensor group of largest expected information gain per call, the mutual information by Monte Carlo, among the groups the window can still serve, one call each with the step cap as the budget, and stops when the flag of `decide` is off and the top combination equals the truth, or when no read is left. A commitment to a wrong combination does not stop that search, and the rollout records whether its first commitment named the truth. The entry of a combination holds the mean cost and the mean readings of the rollouts that commit to the truth, their share `commit_share`, and `first_share`, the share of rollouts whose first commitment names the truth, and a combination on which no rollout commits to the truth has no entry. Both labels start from a uniform prior and read no past order, while the belief of the CausalDiagnosis MCP on a row that serves the maintenance history weighs the initial combination by the released past orders. The rig's own action surface records nothing before cycle 0 and serves live recordings instead, so a label read there describes the serving of the AssetOpsBench rows, whose record every rollout reads. The binary label takes the rule of the independent label, the majority over the rollouts, so an initial combination is diagnosable within the budget under E18 when `first_share` is above one half, and the two labels read one rule, what a rollout commits to first. The grade runs on the fits the CausalDiagnosis MCP runs, one rule for the grade and the CausalDiagnosis MCP, so no rollout is scored by a fit that read the block it reads. The independent label that scores an abstention comes from the environment's baseline policy, and the drivers report both labels, with Cohen's kappa over the two binary labels, the rank correlation of the label's share with `first_share`, and the correlation with `commit_share` beside it.

**E19, transfer.** No formula names the rig. The asset enters through the view of `profile_view`.

**E20, the candidate plans**, in [Candidate plans](#candidate-plans).

**E21 and E22**, in [Information gain and the read batch](#information-gain-and-the-read-batch).

## Ranking root causes

`rank_root_causes` replays the released evidence through the filter of the configured ranking model, computes the costs E7 at the current cycle and the decision E10 with every reading drawn from the belief it meets, and returns the first `top_k` combinations with positive mass now, by mass and then by the combination in component order, with `more_candidates` counting the rest, with their fault codes from the failure modes of the asset profile and the released values whose channel indicates a faulty component, the fault probability and the level distribution of every component now, the attribution E4, the stability E6, the decision fields with the separating test (its group, one cycle, its price, its duration, its cost and the expected loss after it), the unseparated components with their channels, the information gain, the expected elimination and the one step edge cutting score of every read and the read batch, the Monte Carlo count, seed and standard errors, the costs the decision used, the number of augmented states, the number of resampled fits, the effective number of hypotheses and the cycle of the belief, and the candidate plans. The default detail `compact` leaves out the level distributions, the attribution E4, the stability E6, the edge cutting scores and the Monte Carlo settings, gives each candidate root cause the newest reading of every summary that bears on it beside the closed orders, and holds one assumption text, which says so. The details `summary` and `full` return them with every assumption text.

The rule of the CausalDiagnosis MCP reads the record once before a diagnosis, and its fields stand at the top level of every detail. On a row whose rules price nothing the read is, of the sensor groups the row can still serve, the one that can still show the most summaries not yet shown, for every recorded cycle that no reading of the group has shown, when the call fits the calls left beside the work orders that repair the top combination, the diagnosis and the finish. On a row whose rules hold a price the read is the group that can still show the most summaries and that the budget pays beside the repair of every component, for the cycles the money left pays. What a row can still serve a group counts the recordings shown since the last released closure, and the group is open until it has been shown one window of recordings that hold all its summaries. On a row that reads a record its cycles are those of the record since that closure, the window before the episode and every cycle the clock played that no repair stopped, whose recording lacks a summary of the group or was never read, and on a row that plays a recording per read they are the window less the recordings shown. `left_to_read` reports these cycles per group, all zero when no read adds evidence that the rule would use. `read_first` is true exactly when the rule names that read, `separating_test` is the read with its cycles, and `read_batch` holds it and the reads the rule names after it in order. After each read the summaries of its group count as shown on its cycles, until the rule names no read or `BATCH_CAP` reads stand, so on nested groups the batch is the one read. `advice` names the read while there is one, and else the diagnosis of the most probable combination with one work order per faulty component, under the decision rule never a declaration, with `declare_above`, per measure of the verifier, the chance of an initial combination that both labels mark not diagnosable within the budget above which a declaration would score more. No advice follows a diagnosis or a declaration. The details `summary` and `full` add the block `e10_rule`, the earlier rule that the read and repair choice ablations of the agent read, E10 with the launch option `e10_margin`, whose flag is `read_first` with its `separating_test` for one cycle, and E22 with the launch option `batch_cap` and the reserve of the launch option `reserve_plans`, whose batch is `read_batch`. The detail `compact`, the default, leaves the block out and runs no search of E22, and the three fields of the card act on the block alone.

In `summary` and `full` the assumptions name the fit, E1, the prior and the kernels of E2 with the source of every rule card, the readings that show one recording, the block variant or the urn when they apply, the state count, the predict step, E3, E4, E6, the cost rule with the prices behind it, the abstention rule, E21, E22, the candidate plans and the time convention. The compact reply holds one text instead, which names what it leaves out.

## Information gain and the read batch

**E21, information gain per unit cost.** The effective number of hypotheses of a belief, the perplexity of the belief, is N(b) = exp(H(b)), the Hill number of order one, which equals m when the belief is uniform over m combinations and is reported as `effective_hypotheses`. The information gain of a test a is IG(a) = H(b_a) minus the mean of H(b_{a,y}), the expected drop of log N(b) in nats, with b_a the belief the reading of one cycle meets and b_{a,y} that belief updated with a reading y drawn from its predictive, from the same seeded draws as E9. The gain is the mutual information between the combination and the reading, so it is never negative in expectation. A mean drop within `ROUNDING` of the belief's entropy is the rounding of a belief that the reading cannot move and counts as zero, as does a Monte Carlo mean below zero. `ig_per_cost` divides the gain by the test cost of E7, `cost` with its `cost_unit`, a cost that exists on every row of the environment table: the read price plus the declared duration times the expected downtime rate from the priced row on (`money`), and one call on the free base row (`call`). A read that costs nothing has a rate of zero, since a reply cannot hold an infinite rate, and its gain stands in `information_gain`. `ig_per_cost` ranks the reads. The rule is the information heuristic of sequential fault diagnosis, which Pattipati and Alexandridis 1990 describe as a one step look ahead that selects the test of largest information gain per unit cost. When the belief is uniform over n combinations and the reading of a falls exactly on classes of m_o of them, IG(a) is ln n minus the sum of m_o over n times ln m_o, the expected elimination below is n minus the sum of m_o squared over n, and the expected elimination per cost is the rule of generalized binary search with costs (Dasgupta 2004, Golovin and Krause in the revision of 2017). The gain per cost picks the read of that rule when every read has two outcomes and the same cost, and with more outcomes or unequal costs the two rules can rank reads differently. No approximation guarantee is claimed. The guarantees of generalized binary search and of its successors need readings with finitely many exact values, a monotone objective, test costs that do not depend on the belief and a state that does not move between reads, while the readings here are Gaussian, the test cost follows the expected downtime rate and the predict step moves the state on the timed rows. E10, the earlier rule of the block `e10_rule`, looks one read ahead, so its `read_first` can be false when only a pair of reads would lower the expected loss of acting, and its read batch is then empty.

The expected elimination EE(a) = N(b_a) minus the mean of N(b_{a,y}), with its Monte Carlo standard error, and its rate `elimination_per_cost` stay in every row of `elimination` as the reported count of the combinations a read is expected to rule out. EE does not rank the reads because it is not monotone. With nine tenths of the mass on one combination and the rest uniform over eleven others, the read that tells that combination from the rest has an EE of N(b) minus 0.9 minus 0.1 times 11, below zero, and a gain of H(b) minus 0.1 ln 11, above zero, so a rule that admitted only reads of positive EE would leave that read out. Both scores count combinations with their levels, so they value a read that separates two combinations with one faulty set, which the diagnosis score needs and which E10 weighs only through the price of a wrong diagnosis, and on the free base row through the calls left before the step cap, the loss of a failed episode.

**One step edge cutting, reported for the read choice ablation.** `ec2` is one step edge cutting over the classes of the repair decision, after the EC2 objective of Golovin, Krause and Ray, not their algorithm. It is the expected weight of the edges between the plan classes of the repair loss of E8 that one reading of the group cuts, and `ec2_per_cost` divides it by the same cost. The classes leave out the price of a wrong diagnosis, so the cut stays with the read that decides the repair. Every combination h with mass b(h) carries `EC2_DRAWS` seeded readings of one cycle of every group, each of weight b(h) over `EC2_DRAWS`, which draws the reading noise into the hypotheses. The outcome of a group's reading is the set of work orders of least expected repair loss after it. The readings with equal outcomes on every group form one hypothesis, whose class is the set of work orders of least expected repair loss given those outcomes, and an edge between two hypotheses of different classes weighs the product of their masses. Finer outcomes are not used. Bins of every summary of a group, or the combination of largest mass after the reading, let the reading noise split the draws of one combination into many outcomes, so that every read cuts nearly every edge whatever it measures. With plans as outcomes, a read whose reading alone never changes the plan cuts nothing, the one read horizon that E10 shares. The CausalDiagnosis MCP ranks nothing by it. It is reported so that the third arm of the read choice ablation can rank reads by `ec2_per_cost`, and no approximation guarantee is claimed for it on the Gaussian readings. The details `summary` and `full` report it, and the compact reply computes no cut and holds null in both fields.

**E22, the read batch.** `read_batch` holds the reads of the rule of the CausalDiagnosis MCP in order ([Ranking root causes](#ranking-root-causes)), one read on nested groups. The batch of E22 is `e10_rule.read_batch` in the details `summary` and `full`, and the detail `compact` runs no search for it. While `read_first` of the block is true, the batch starts with the affordable read of largest `ig_per_cost` above `IG_EPSILON`, ties falling to the cheaper read. A further read joins only when it has the largest gain per cost, above `IG_EPSILON`, under each of `BATCH_OUTCOMES` simulated outcomes of the reads before it (`BATCH_INNER_SAMPLES` draws per group under each), so that waiting for those outcomes could not change the choice, with no count of its own: it ends where the simulated outcomes name different groups or no group gains, or where the budget, the horizon or the step cap leaves no room for a further read beside the reserve, or at most the launch option `batch_cap` of the CausalDiagnosis MCP where it is given. The reserve holds the repair and the read that verifies it as the agent's plan check prices them: the cheapest group whose reading verifies the new components, those of the open work orders and those of the repairs whose verifying reading is still to come. `IG_EPSILON` keeps a gain that rounding left at zero out of a batch. The read prices must fit the budget left after the price of the work orders that repair the top combination with its visit charge, and under the card's `reserve_plans` 2 also of the cheapest candidate plan of another combination of the credible set, the candidate plan that backtracking turns to, and the reads must leave the cycles of that candidate plan before the horizon. On the free base row, whose status carries no budget, the reads and the plan's one call per order must fit the calls left before the step cap. Every entry of the batch carries the `information_gain`, `ig_per_cost` and `elimination_per_cost` of its row of `elimination`. The batch holds the belief fixed between its reads, an approximation over the few cycles a batch spans, which the assumptions state.

## Candidate plans

`rank_root_causes` walks each distinct faulty set among the returned combinations forward to a restored rig and returns the result as `branches`, one entry per faulty set, each a candidate plan of E20. The advice and the read-first rule still read every combination with positive mass. A plan repairs a faulty set, so the combinations of one set share one plan, one walk and one `plan_prediction_id`, and the number of plans is at most the number of nonempty sets of components plus the healthy set, whatever the number of combinations. The argument `branch_detail` chooses the view of the plans: `compact`, the default, and `summary` leave out the two largest fields, `predicted_outcome.predicted` and `confirm_test.gap_by_group`, and hold every other field, since an agent that reads raw tool results pays for every byte of them, and `full` returns them. The plans and their computation are the same in the three views. The rig cannot be repaired once per combination to see which repair works, so the walk forward happens in the CausalDiagnosis MCP. Every quantity of a candidate plan is a mass of the belief, a price, a duration times a downtime rate, or an expected loss of E8 or E9, computed with the Monte Carlo sample count of the CausalDiagnosis MCP and a seed equal to `MONTE_CARLO_SEED` plus the rank of the candidate plan, so a replayed call returns the same candidate plans. The decision fields of E10 and E12 stay as they are. The candidate plans are decision aids over the public prices, durations, downtime rates and the belief, never the cost the environment charges, which the assumptions of the result state.

| Field | Content |
| --- | --- |
| `rank`, `ranks`, `combination`, `current_combination`, `probability` | the rank of the set's most probable combination, the ranks of the returned combinations with this faulty set, that most probable combination now in both fields, and the mass of those combinations, their sum |
| `faults`, `faulty_set` | the components of the combination off their healthy level, with their codes, and their names in component order: what the candidate plan would repair |
| `confirm_test` | the sensor group whose next cycle separates the combination most, with `cycles` 1, `price`, `duration`, `cost` (E7, the `test_cost` the decision uses), `mass_if_true`, `mass_if_false`, `gap`, `standard_error`, and `gap_by_group` with the gap of every group in the `full` view (null in `compact` and `summary`) |
| `two_step` | the pair of groups, cheaper first, whose two cycles separate the combination most, when its gap exceeds the best single gap by more than `SEPARATION` standard errors of the difference, else null: `sensor_groups`, `cycles` 2, the summed `price`, `duration` and `cost`, and the same four measures |
| `repair_plan` | the plan as one technician visit: `steps` in the order the technician repairs them, priority order with ties in component order, each with `component`, `part_price`, `repair_charge`, `lead_time`, `repair_downtime`, `close_offset` (the cycle after creation at which it closes), `downtime_cost` (the downtime rate of the stopped asset over its repair downtime), `depends_on` (the components its repair needs healthy) and `dependencies_in_plan` (those the plan repairs), and `prediction_id`, then `plan_prediction_id`, the prediction after every repair of the plan that each of its work orders cites (the step's own identifier for a plan of one step, null for an empty plan), `visits` (one, or zero for an empty plan), `visit_charge`, `price` (the parts, the repair charges and one visit charge), `lead_time` (the longest lead time, after which the technician arrives), `waiting_cost` (the expected downtime rate over that lead time), `downtime_cost` (the waiting cost plus the stopped downtime of the steps) and `cycles_to_restored`, the last close plus one cycle for the reading that verifies the repairs |
| `predicted_outcome` | `predicted`, the summaries after the plan with their conformal intervals at `alpha` (E13 through the plan's closures, then E14) in the `full` view (null in `compact` and `summary`), `recovery_if_acted`, the predicted mass of the healthy combination at the first reading after the plan, and `restored_if_true`, whether the plan restores the combination when nothing else happens, which fails when a repair depends on a component that is still degraded when the repair closes |
| `expected_loss_if_acted` | E8 of acting on the set's most probable combination, the one a diagnosis submits, its row of the loss times the belief, the expected repair loss of its faulty set plus the price of a wrong diagnosis times one minus its mass, so for the first candidate plan the ranking's `expected_loss_act` |
| `expected_loss_if_tested` | E9 after the confirm test with its cost, the ranking's `expected_loss_test` of the confirm group, from the same draws under the mixture of all combinations |
| `cost_to_restored` | predicted costs: `act_now`, the plan's price and downtime cost plus the belief times what acting on the set's most probable combination can cost beyond the outlay of its plan, the faults the plan leaves and the price of a wrong diagnosis, or on the free base row the calls left once for an act off the truth, so that an unnecessary replacement counts once, in the price, and `test_first`, the cost of the confirm test plus, averaged over the drawn readings of that test, the price and downtime cost of the plan of the combination that is first after the reading and that reading's belief times its loss beyond the outlay of that plan |

**The confirm test.** For every sensor group, the CausalDiagnosis MCP draws one hypothetical cycle of the group under the combinations of the set, from the predictive of E1 on the belief the reading meets with its mass on those combinations in proportion to their mass, and updates that belief with each draw (E2), as `Posterior.sample_next` and `update_with` do for the decision rule. The mean of the set's updated mass over the draws is `mass_if_true`. The same with draws under the mixture of the other combinations, their masses renormalized, gives `mass_if_false`, the mass the set keeps when it is wrong. For a set of one combination this is the test of that combination. The `gap` is the difference and its standard error combines the two Monte Carlo means. The confirm test is the group with the largest gap, a tie falling to the cheaper group. Two step pairs, every pair of groups including a group read twice, are measured the same way with the two cycles stacked into one reading whose covariance holds the within covariance of each cycle and the shared latent block offset between them, which is the exact sequential update whatever the order, so the pair is reported cheaper group first. A pair is reported only when its gap exceeds the best single gap by more than `SEPARATION` standard errors of the difference, the joint evidence case in which one reading alone does not separate the combination.

**The work orders of the candidate plan, `repair_plan`, and their predictions.** One work order per component of the combination's faulty set, created one after another so that one visit repairs them: the technician arrives after the longest lead time and repairs them back to back in priority order, as `schedule_visit` of the clock runs them, and the visit is charged once. Each step registers the prediction of replacing its component alone under the current belief through the same code path as `estimate_intervention_effect`, and a plan of several steps registers one more prediction, the state after every repair of the plan, exposed as `plan_prediction_id`. All are stored in `predictions.json` as `pred/b{n}` with the fields of the intervention tool's records and a `branch` key holding the rank that registered them, and a plan record carries its `components`. The separate numbering keeps the `pred/{n}` identifiers of the intervention tool unchanged, and a prediction whose action is already stored for the same released evidence cites that record, so a ranking replayed on unchanged evidence stores nothing twice. The rule for an agent that executes a plan: every work order of the plan cites `plan_prediction_id`, and one reading after the last order closed verifies it. Only a reading after the last close shows the state the plan predicts, which is why a step's own prediction is for a single order executed alone. The verifier scores every work order by the recovery its cited prediction promised against the final state, so citing the plan's prediction on every order scores the plan, not a part of it.

## Estimating an intervention effect

`estimate_intervention_effect` takes `replace:<component>`, a standard order, or `monitor`. It runs the belief through the action (E13), predicts every summary with its conformal interval (E14), those of the predicted combination, the most probable after the action, which the message names with its mass, reports the risk before and the predicted risk after with the direction (E15), the price and the duration of the action from the released rules (the part plus the repair charge plus one visit charge, the lead time plus the repair downtime, and as the downtime during the action the expected downtime rate over the lead time plus the downtime rate of the stopped asset over the repair downtime), and appends the prediction to `predictions.json` as `pred/{n}` with the number of events and observations released so far, the time, the predicted belief after the action, its most probable combination, the predicted combination, with its mass and the predicted intervals with their alpha. The assumptions flag an action the environment would refuse: a work order on a component whose order is open, a repair before a diagnosis or a declaration, or any action after the episode is over.

## Verifying an outcome

`verify_outcome` compares a stored prediction with the first reading that shows the closure of the component's work order that closed after the prediction, a reading released after the closure and recorded at or after its cycle, or, for `monitor`, with the first reading released after the prediction and recorded at or after its cycle, since a later read can release an older recorded cycle. The plan prediction of a candidate plan, whose record names several `components`, is compared with the first reading that shows every one of its components' closures, and only the closures of components outside the plan that this reading shows make it not comparable. The reading must hold an indicating channel of every repaired component whose indicating channels the released events show the agent was told, by an answer of `lookup_fix` on any row or by the failure modes on a row that does not read a record, and every channel of the asset for a component it was told none of, as the agent's own check judges it (`public_rules.repair_completion.verifies`).

| `status` | When |
| --- | --- |
| `not yet observable: the work order is open and has not closed` | an order on the component, or on one of a plan's components, is open |
| `not yet observable: no work order on the component has closed since the prediction` | no order on the component, or on one of a plan's components, closed after the prediction and none is open |
| `action refused: <reason>` | the environment refused a work order on the component after the prediction and none closed |
| `not yet observable: no reading since the action` | the repair closed, or `monitor` was predicted, and no reading followed |
| `not comparable: <actions> closed between the prediction and the reading` | an order on a component the prediction does not replace closed after the prediction and before the reading, so the reading can show another combination |
| `verified` | a reading followed the action, and the channels, the verdict and the recovery check are filled |

The message of a verified result names the combination the verdict scores against and its mass, the fields `predicted_combination` and `predicted_mass`, and `recovery_posterior` is the mass of the healthy combination in the belief of the filter now, the number a ranking on the same released evidence reports. `level_reachable` says whether the calibration blocks carry alpha, and the message says so when they do not. A prediction whose work orders were created after its estimate, after thinking time or other calls, is made again for the cycle of their creation, from the evidence the estimate held and with the rule cards running through the cycles in between, and the message says so. A plan whose orders were created in several cycles is made again for the last of them, as one visit. A second order on the same component after its closure is not flagged here. The verifier of [environment.md](environment.md) counts it as unnecessary when the component was healthy.

## Running the CausalDiagnosis MCP

A copy of `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/launcher.py` beside the `released.json` of an episode binds a process of the CausalDiagnosis MCP to that episode. The launcher accepts `left_out=<levels joined by commas>`, the initial combination of the episode, whose recorded block every fit of the episode leaves out, which the driver always passes, and the optional `key=value` arguments `ranking_model=joint_block|joint|discriminant_urn`, `abstention_rule=decision|fixed_cut` and `abstention_cut=<probability>`, forwarded to `main`, so a driver selects the arms of the ranking model and stopping rule ablations per episode. It also accepts three launch options, `e10_margin=<number>`, `batch_cap=<integer>` and `reserve_plans=<integer>`, cast to their types, which keep the constants of the CausalDiagnosis MCP when absent, where an absent `batch_cap` means no count and act on the block `e10_rule` alone. The process serves the Model Context Protocol over stdio and waits for a client:

```bash
cp CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/launcher.py /path/to/episode/causal_server.py
PATH=$PWD/.venv/bin:$PATH PYTHONPATH=src python /path/to/episode/causal_server.py left_out=<levels>
```

The `causal-diagnosis-mcp-server` script of `pyproject.toml` starts the CausalDiagnosis MCP without an episode, in which every tool answers an error that says so. The AssetOpsBench runners register by default only the servers of `DEFAULT_SERVER_PATHS` in `src/agent/runner.py`, so the CausalDiagnosis MCP reaches a runner through `server_paths`. `CausalDiagnosis/experiments/episode_runners/run_episodes/` calls `ensure_models`, creates each episode and writes one launcher per server into its folder with `write_launchers` of `CausalDiagnosis/experiments/episode_runners/episode_launchers.py`. These launchers put the fork's `src` on the import path themselves, since a process of the CausalDiagnosis MCP receives almost no environment variables, name the ranking model to run and the initial combination of the episode, and name the abstention rule when it differs from the default. The driver takes its default ranking model from `DEFAULT_RANKING_MODEL` of this package, so the two cannot drift apart.

## Known limits

- The parameters of the rule cards come from the `processes` block of the released rules, which `write_released` of `CausalDiagnosis/mcp_servers/Environment_Actions_MCP/episode_state.py` puts into every released file. A released file without the block is filtered under the default configuration of the asset profile.
- The conformal calibration and the urn arm leave out the block of the initial combination alone, and the selection of interactions the block of the initial combination and its second block, so a competitor's own block takes part in them, which [The models file](#the-models-file) and [Ranking models](#ranking-models) justify. The blocks that leave the fits are named at launch, so the readings after a repair are not scored as cleanly as those before it.
- The calibration check of the selected pairs is one sided. A unit test checks that the fits with the selected pairs read fewer wrong answers than a main effects fit built by the same rule on every kind of row, and that the gap between the top mass and the accuracy does not lie above the size of that fit's gap, since being too sure is what misleads an agent. The reference of that test is built under the registered default estimator, so the test compares the pairs and the estimator at once and cannot tell which of the two a failure comes from. The offline table prints the like for like comparison and both tests of the gap beside it.
- The interval of E14 and the verdict of E17 are those of the most probable combination after the action, so a belief spread over several combinations shows in the mass the verification names beside that combination, not in the width of the intervals.
- The decision of E10 compares a Monte Carlo estimate with the loss of acting, so when the saving is within the reported standard error `read_first` of `e10_rule` can turn with the seed. The result carries the standard error per test, and the sample count is one declared constant. A priced wrong diagnosis multiplies that error by its price.
- The price of a wrong diagnosis is a design parameter like the other prices, which the environment charges at a wrong diagnosis, so how many reads E10 buys for the levels scales with it. The rule of the CausalDiagnosis MCP weighs it in no advice.
- The rule of the CausalDiagnosis MCP is static and looks no further than the reads it names before a diagnosis. The count of what a row can still serve ends at one window of recordings since the last closure, so on a row with a clock later cycles can still show recordings that no reading has shown, and a level drop or the end of an emergency hold, which no public event names, opens a new window that the count does not start again. A first read made after more than one window of played cycles pays for cycles that repeat recordings of the same read. A history window that would first play cycles is not scored as a test, and a cycle that the clock records later is counted then.
- A recording served again after its window wrapped is recognized when it shares a summary with an earlier reading of the recording, so a repeat read through fields that no earlier reading of the recording holds enters the belief as a further cycle. A reading that repeats after a closure a recording first shown before it joins that recording at its first cycle, so it adds nothing to the belief after the closure, and what a repair changed is read from `verify_outcome`, whose check takes the readings after the closure alone.
- A row without a clock that lists a wait could be made to play live recordings, which no registered row does, and both labels describe its record before any wait.
- The filter does not read the change summary's alarms or the failure events, so the belief is a posterior on a subset of the released evidence.
- Under the stochastic hazard the number of states grows with the cycles of the episode, and the filter then carries fewer resampled fits for E6, as `resampled_fits` reports.
- The discriminant and urn arm keeps the fixed constants of the discriminant classifiers (`SHRINKAGE`, `ALPHA_GRID`, the fold count), and it serves the comparison with the joint model.
- An ablation that changes any key of the grade table computes its own table on first use.
- Under the Plan-Execute executor every tool call costs one process start, one parse of `models.json`, one build of the fits of the episode and one replay of the whole released history.
- The predictions of a plan's steps describe one replacement each, so when two orders of one plan close before the next reading, `verify_outcome` reports each step's prediction as not comparable.
- A two step pair is measured as a fixed pair of reads, not as an adaptive policy that chooses the second read after the first result, and the candidate plans add Monte Carlo draws per combination to every call of `rank_root_causes`.
