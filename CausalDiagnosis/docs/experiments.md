# Hydraulic Rig Drivers and Result Tables

`CausalDiagnosis/` holds the episode driver of the hydraulic rig gym, the audit report that every episode writes, the configuration presets and price tables, the fetch and the anchors of the anchored scenarios, the statistics, the ablation tables, the leaderboard, the judge, the online loop of GEPA, the publisher of run folders, and the scripts that fetch, rebuild and check the rig data. One command plays episodes with an agent or a baseline policy through the rig's action server and the CausalDiagnosis MCP, or with an agent through AssetOpsBench's servers and the task server under `--servers aob`, and verifies every episode from its log. This page covers the runtime, the options of every script, the files a run writes, and the columns of every table.

Related docs: [README.md](README.md) for the overview and the data file, [environment.md](environment.md) for the episode rules, the oracle and the verifier, [environment-actions-mcp.md](environment-actions-mcp.md) for the twelve action tools, [causal-diagnosis-mcp.md](causal-diagnosis-mcp.md) for the four diagnostics tools, and [../running_benchmark.md](../../docs/running_benchmark.md) for the upstream benchmark run.

Names on this page follow the code and the texts that an agent reads, and the [glossary](README.md#glossary) of the docs README gives the term of the paper for each of them, such as configuration for preset and for row and abstention for declaration of insufficient evidence.

## Quick start

```bash
# 0. the rig data file, built once as in CausalDiagnosis/docs/README.md
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis datasets download hyd_1 --check

# 1. one scripted episode through both servers, without a model
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-episodes --config static --agent scripted --seeds 1

# 2. the oracle policy and the do nothing policy through the action server on the same seeds
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-episodes --config static --agent oracle --seeds 3
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-episodes --config static --agent do_nothing --seeds 3

# 3. the ablation tables from every run folder, with their design and empty cells where no run contributes
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis tables all

# 4. the output
ls CausalDiagnosis/results/runs/ CausalDiagnosis/results/tables/
```

Every command on this page runs from the fork root with the environment's `bin` first on `PATH`, since the Plan-Execute runner starts every tool server as `python`. A run folder is named after the configuration preset, the agent and the start time, as in `static_scripted_<YYYYmmdd-HHMMSS>`, with the dots and slashes of a model name turned into underscores.

## Runtime

The driver needs the environment and both servers, the MCP client and server, the OpenTelemetry API that the Plan-Execute runner imports, and the OpenAI SDK of its OpenAI compatible backend. The slim virtual environment of [README.md](README.md) holds them at the versions `uv.lock` pins, and `uv sync` installs the whole fork instead, in which `uv run python` replaces the `PATH` prefix. Every script of the folder puts `src/` and the folder itself on the import path, so no `PYTHONPATH` is needed. Before the first episode that registers the CausalDiagnosis MCP or looks a grade up, the driver fits `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/offline/models.json` when it is missing.

| `static` | no server | ablation Sc3 (table A3): one model call over the question, the features of the recorded cycle the gym would have served first (read from a throwaway environment at the full sensor group, features only and never a label) and the failure modes. The answer is judged against the oracle's reference answer and parsed for the components it calls faulty and repaired |
| `oracle`, `do_nothing`, `greedy`, `random`, `declare` | the action server | the baseline policies of [environment.md](environment.md), each action sent as one tool call through the runner's own stdio helper (`play_policy`). A shadow environment in the driver process is reset with the same seed and configuration, the oracle reads the hidden state from it, and after every call the shadow steps the same action with the thinking cycles the server stored, so the served log is compared with the shadow's (`replay_matches`). A Plan-Execute run plans until the reviewer accepts a plan or five plans are written, executes the plan step by step and summarizes. An Agent-As-Tool run takes supervisor steps until the supervisor writes Finish, runs out of its 10 steps or stops on a loop, or until the environment ends the episode, and every call of a sub-agent takes that sub-agent's own steps. A causal run plans again after every surprise and after a plan runs out of steps, until the controller finishes or the budget, the horizon, the step cap or the wall limit ends the episode. An episode that the plan leaves open stays open and is verified as it stands, with the count gate failing on the missing finish. A run that raises, such as a plan with a malformed dependency or an API error that outlasts the client's retries, leaves its message in the `error` column, and so does a verifier that cannot read an episode. Before the first episode the driver lists the tools of every registered server once, on a scratch folder that it removes again, and stops when a server offers other tools than the contract names (`check_servers`).

The controller compacts the working memory of the `causal` agent after every executed step, while no model call is pending. With the CausalDiagnosis MCP the evidence rows that the latest ranking has absorbed collapse to one summary row per sensor group, whatever their size. The further steps run only while the tokens of the next planning prompt alone exceed nine tenths of the served context, rounded down, the compaction trigger. Past the trigger the latest absorbed observation collapses too, and without the CausalDiagnosis MCP the absorbed rows collapse only past the trigger. Past it still, one model request headed `## Summary of your earlier turns` summarizes the notes, the notifications, the surprises but the latest and the timeline older than the latest ranking, and the summary stands on the board as `## Your summary of earlier turns` in place of those entries. The summary request is sent only when the board without those entries would be under the trigger, or when the planning request no longer fits the whole context, and a request that still does not fit ends the run as `context`. Every refuted plan retains its line and every collapsed identifier remains citable. A plan step `recall`, with a sensor group and the first and the last observation, brings the full rows of collapsed observations back under `## Recalled readings` on the next planning board alone. The step calls no tool, so no price is charged for it, a turn of recalls alone takes the `no_call` step, and rows that would not fit the whole context are dropped and logged. The summary turn and the recall step play in every run, and no option turns them off.

Both ports run on every row with the settings of the AssetOpsBench paper's code. The Agent-As-Tool supervisor takes at most 10 steps with one reflection round, and its sub-agents take at most 15 steps for IoT, 6 for TSFM, 10 for FMSR and 20 for WO, and 10 for an agent that the paper lacks, each with one reflection round. Plan-Execute writes at most five plans with three attempts of the reviewer, asks the summarizer at temperatures 0, 0.1 and 0.2, and runs each step agent with at most six steps and one reflection round. Every ReActXen agent of both ports applies ReActXen's loop rule with its early stop, its alarm of 300 seconds on an action and its handling of a full context, and every request asks for at most 500 tokens. After each step of a ReActXen agent whose scratchpad holds more tokens than the served context, `truncate_scratchpad` of the vendored ReActXen replaces the longest `Observation` lines, the longest first, by their label and `[truncated excerpt]` until the scratchpad fits. A request that with its 500 tokens no longer fits the served context ends the run with the reason `context`, as does an Agent-As-Tool supervisor whose prompt passes the context. No client or tool call of the ports has a time limit of its own, and the deadline of the row bounds each of them.

Every agent plays under one harness rule, that of `EpisodeRunner.play`. The runner's part of an episode has a wall limit of 1800 seconds, `EPISODE_WALL_LIMIT_S`, the value that the upstream repository sets for one agent run, which no option changes and which both briefings name among the ends of an episode. When a runner stops and the environment has not ended the episode, the driver ends it with one finish whose summary is the runner's own answer, through the code that serves the task tool `finish` on the surface of the row, stamped with the end of the runner's last model call, so every agent is charged its last model call and the open work orders settle as after a finish of the agent. On a row with a thinking clock the driver first takes one `no_call` step with the same stamp, which charges the thinking accrued up to it and counts one step of the step cap. When that step ends the episode, at the horizon, by a failure, or at the step cap because it was the last step left, no finish follows and the open work orders do not settle. The class of a failure is decided at run time from the type of each error, by `attempt_error_classes.py`. An error of the connection, a status of 408, 409, 429 or 500 and above, a refused key or an unknown model, a tool call without an answer and a step of the harness that raised are the infrastructure's, a request the endpoint refused, a context overflow among them, and every other error are the agent's, and a timeout is the agent's while one request for the model list of the endpoint is answered. A cut at the wall limit is classed first, by what was open at the deadline. A wait after a failed model request or a counted call of the action servers that has not returned makes it the infrastructure's, and so does an open model request while one request of a single token to the model service receives no answer, and nothing of the agent's time is played. A call of the CausalDiagnosis MCP is no counted call, and neither is a `no_call` step of the driver, so a cut inside one of them is classed by the other facts, and with none of them open the cut is the agent's. A cut of the agent leaves the thinking accrued up to the deadline charged at the deadline itself, not when the harness reaches the episode after its sessions closed. An attempt of the infrastructure is set aside without such a finish in the folder `attempt1` of its episode and played once more under the same seed, a second one gives the row the class `harness_error` with empty scores, which counts as a failure, and three such rows in a row stop the run with exit status 75 and no `run.json`, so its grid line remains pending. Every episode folder holds `harness.json` with the attempts, the class, the finish and the end of the runner.

Some values are declared in the code, each with its reason. The harness guards of a run are one replay of an attempt that the infrastructure broke, a stop after three harness errors in a row, a health check of 10 seconds, and the limit of 12 hours of a cluster job, which ends no episode, since a run resumes in the next job. A model request inside an episode carries no read timeout of its own, and the wall cut of the row ends it as it ends a tool call, while a model request outside an episode, a reflection, a judging or a summary of training, waits at most 600 seconds for its reply and 5 seconds for its connection. The rule covers the agent's own work inside an episode, its model requests and its tool calls, and the listing of the served model and the count of tokens that `CausalDiagnosis.utils.model_reply_room` asks for go through the same retry policy as the model requests. The harness's own calls, the probe at the cut, the cache flush, the opening check and the state reads, run under their declared timeouts, and a failed one is an attempt of the harness, never an end of the agent. The other declared values are the ten stable recordings that each fault combination serves, the bound on the search for the development split, the largest cost ratio that the reward charges, the five records of the one history read of the scripted reference plan, the declared length of the Gymnasium text spaces, and IBM's own retries, page sizes and query sizes in its servers. The compaction trigger, nine tenths of the served context, is the share of the context window at which the Codex CLI compacts its own history, and it decides when the working memory of the `causal` agent is compacted, never when a run ends. None of them bounds what the CausalDiagnosis agent, the action server or the CausalDiagnosis MCP does in an episode.

The environment rows start every server through the MCP client, which passes no model variable to the FMSR server, so its generate tools are off there and no row of the environment tables plays through the LiteLLM backend of `src/llm`. The reproduction of `CausalDiagnosis/frameworks/AssetOpsBench/reproduction` starts the FMSR server with its model variables, as IBM's code reads them, so its generate tools reach the LiteLLM backend through `make_backend` and ask for replies of at most 2,048 tokens, IBM's default reply length.

The plan check of the CausalDiagnosis agent keeps only the rules that do not come from the CausalDiagnosis MCP, and a plan that breaks one goes back to the model with the reasons. What the CausalDiagnosis MCP advises, the reads before a diagnosis while the ranking says read first, the candidate plan to act on and the candidate plan after a refuted one, never refuses a plan. The rules follow, one per line.

1. The reply holds one JSON plan with a known mode and, when `--causal-plan-length` sets a count, no more steps than that count once the joined components of an order are split, each step of a known kind with valid arguments and expectations, and finish only as the last step.
2. Before the profile is read the plan holds only the steps of the opening, and it reads the profile before the failure modes of a component and before the extent of the record.
3. A step names a sensor group or a component that the profile holds and a rank among the candidate root causes shown, and a time or extent step comes only on a row whose readings need it.
4. On a row whose readings need the time and the extent of the record, a reading comes after those steps.
5. A diagnosis names a candidate root cause of the ranking or one that the plan lists, whose components and levels the profile holds.
6. A declaration cites a reading, so a reading comes before it.
7. A diagnosis or a declaration comes before every work order, and a second one is refused, as the environment refuses it.
8. A work order names a component that has no open or planned order.
9. Finish comes after the close of every work order and, wherever a cycle runs after a close and a read fits, after the reading at or after the last close that verifies the repair.
10. The prices fit the budget left, the cycles end before the horizon and the tool calls fit the steps left.

Every run passes the start check of `run_episodes.registration` before any table is fitted and before the run folder exists. A run is a run of record when the check finds no reason, and the commit that the run records is its record, so a fault found later is fixed in a new commit and the rows that the fix changes are played again at that commit. The check reads ten rules in this order.

1. The tree is a git repository at its own root, so it names a commit. A copy that `CausalDiagnosis/cluster_jobs/0_setup/upload_fork.sh` sends names none and plays development runs alone.
2. No file under a code root differs from the commit, and no file of the tree lies in no list.
3. Every file that the driver process loaded, `loaded_files` of `run.json`, is tracked at the commit and equal to it, so an ignored file that a process imports cannot pass.
4. The commit stands on a branch of `origin`, so others can check it out.
5. The data of record pass the pins of `CHECKSUMS.txt`, and the generated tables are those of this tree.
6. `registered_analysis.json` holds no open value.
7. The serving of the agent model, and of the judge when the run judges in it, equals the serving file of record `serving_of_record.json` beside the scripts in its served name, weights commit, engine image, dtype, quantization, kv cache dtype, chat template and launch flags. A weights commit of the form `config:<sha256>` is refused, and a missing key is a reason.
8. When `GPU_OF_RECORD` of `env.sh` names a card, the card of each endpoint equals it. `run.json` records the card in every case.
9. An episode of a preset with the wall clock plays alone on its card, the declared number of runs in flight, and the harness empties the cache of the model server before each such episode.
10. The start set is `sampled` or `training` on a preset that a table plays, and the preset, the split and the stamps of a trained variant are those of a table.

`run.json` records beside them the commit and whether it stands on `origin`, the platform, and the process settings that AssetOpsBench's servers read, each with its value. The runs in flight of a run are the processes that play episodes against its served model at once, the runs of grid lines, sampling runs and loops of GEPA alike. Its job hands that number down as `GRID_PARALLEL`, the `N` of the job to a run without the wall clock and 1 to a run on the wall clock, which plays alone, and the check compares it with the number of the preset in `design.RUNS_IN_FLIGHT`. A run with any reason carries `stamp` `development` and its `stamp_reasons` in `run.json`. The GPU card is the name and the memory in MiB of the GPU of the serving job, which the endpoint file names as `gpu_name` and `gpu_mib`. A model agent registers only with the endpoint file of its own endpoint, which names the card, `gpu_uuid`, `driver_version`, `cuda_version` and a `gpu_sampler` file that the node of the run reads, and a run that judges in the run registers only with such a file of its judge endpoint, so that a run of record plays and judges on the card that `GPU_OF_RECORD` names when it names one, and the reason of another card names both cards. A model agent plays an initial combination of the test set of its asset in a run of record alone, which `main()` checks over the whole plan and `EpisodeRunner.start` checks on every episode, so that the loops of GEPA meet the same guard, and no option turns it off. A run of record fits no model and computes no table. `--seeds` below one is refused for every start set that counts seeds.

## The anchored scenarios

The repository holds no record of the AssetOpsBench dataset. `CausalDiagnosis/frameworks/AssetOpsBench/scenarios/download_scenarios.py` fetches its hydraulic scenarios at the pinned revision `REVISION`. They are the `hydrolic_pump` configuration of the dataset's utterance file, as released. The script checks the SHA-256 and the count of records against its pin before it writes anything. It refuses a file that differs. It writes `scenarios_17.json` into the data folder of the asset, or where `HYD_SCENARIOS_PATH` points. Each scenario carries the one date its text names, which equals the date of its `failure_event` field. `--from-file` reads the file of a local clone of the dataset under the same checks. Only the anchored preset reads the scenarios, and a run of it without the file stops with the command.

`CausalDiagnosis/frameworks/AssetOpsBench/scenarios/scenario_anchors.py` maps a scenario date to a recording cycle and to the anchored initial state of an episode. `cycle_of` counts the days from `DATE0`, the first recorded day. `anchor` reads the recorded combination of that day's cycle and its position in the combination's stable block, and a day whose cycle is not stable is anchored at the nearest stable cycle of the same combination, which the result says. `start_of` turns the anchor into the `start` field of `EpisodeConfig`. The mapping rests on two assumptions, `ASSUMPTIONS` of `CausalDiagnosis/frameworks/AssetOpsBench/scenarios/scenario_anchors.py`, which the authors of AssetOpsBench have not confirmed: A1, the asset of the scenarios is the `hyd_1` file with one recorded cycle per day from the first recorded day, and A2, the dates were chosen for the faults the texts name, so the hidden condition of an anchored episode is the recorded condition of the day and not the fault the text names. The `run.json`, `summary.md` and `report.md` of every anchored run print both.

The driver and the ledger reach the scenarios through the declaration of the framework that brings them: `SCENARIO_SETS` of `CausalDiagnosis/frameworks/AssetOpsBench/__init__.py` declares the set `anchored` for the asset `hyd_1`, and `scenario_set` of `run_configuration.py` gives the set of the asset of a run, imported only when a preset anchors its episodes. A preset that anchors its episodes on an asset with no declared set is refused at launch, and two sets for one asset stop the run by name, since a preset names no set.

`--config anchored` plays one episode per scenario under every seed, in folders named `scenario<id>_seed<NNNNNN>`, with the scenario's anchored initial state and its text as the question.

## The judge

`episode_judge.py` is the second scorer of an episode: the rubric scorer of `src/evaluation/scorers/llm_judge.py`, run through the fork's own `Evaluator` on a scenario file and a trajectory record written to a temporary folder, the only input shape the evaluation pipeline reads. The question is the task text of the episode, the characteristic answer is `reference_answer(oracle)`, which names every component's level and failure mode code, the faulty set, one work order per oracle order closed by its window end, and the restored rig, the answer is the closing answer of the runner in `answer.txt`, and the trajectory is the runner's `trajectory.json`, the list of the tool calls with their outputs that the runner of every agent records, the input shape of the released scorer of AssetOpsBench. An episode whose runner left no `trajectory.json` is not judged. The judge reads the trajectory without the cut at 8,000 characters that the released `llm_judge.py` applies, through the scorer of `full_trajectory_scorer.py` that registers under the released name, since that cut retains the head of the prompt and hides the later steps of a long trajectory from the judge, on the rig the diagnosis, the work orders and the repairs. In its place the judge reads the whole trajectory and the whole answer and holds no number of its own; only a prompt that passes the context of the served judge is cut, as described below, by the rule `cut_rule` of `registered_analysis.json`. The code that the AssetOpsBench paper evaluated passed its trajectory uncut, and that trajectory held the steps of the supervisor or the plan with the answers of the domain agents and not the outputs of their tools.

| Protocol | Calls |
| --- | --- |
| `single` | one call at temperature 0, a development option that the tables of the judge do not read |
| `paper` | five calls at temperature 0.3, the default of every judged run, as the AssetOpsBench paper reports, with the average score of the parsed reviews and the pass by the majority of the five planned calls, a failed call counted false |

`judge_episode(episode_dir, backend, protocol, agent_model, base_url, static=False, serving=None, budget=None)` writes `hidden/judge.json` in format 3 with the protocol, the temperature, the planned calls, the judge model as its requests name it, the served name, with its endpoint, its request (`judge_request`, thinking off) and the serving identity of the endpoint that the caller read, the agent model, the cut (`cut`: the served context, the reply tokens of the judge request, the tokens of the whole prompt and of the prompt sent, the records left out, the texts headed with their length, and whether the answer was headed), the SHA-256 of the trajectory and of the answer that the judge read, the task text, the reference answer, the answer, every call's pass, score, rationale, details and error, the pass rate, the mean score and the pass. A call whose scorer result is a backend error, which a call that overflows the judge's context is, an unparseable reply or a missing reference carries that rationale as its `error` and counts as false in the pass rate over the planned calls, as the agents table counts it and as `summary_of` writes it, so the pass is the majority of the planned calls, one rule for the `judge_pass` cell, A3, the leaderboard, the scoring pairs and the agents table, and a record whose calls all failed reads false everywhere until `judge_finished_runs.py` judges the episode again. The Evaluator's rule against self judging stays active, so the judge model has to differ from the agent model.

```bash
export API_KEY=<key>
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis assetopsbench episode-judge --model <judge> --base-url <endpoint> [--protocol single|paper] [--agent-model <id>] [--text-chars <n> --total-chars <n>] <episode folder> ...
```

The command line reads the agent model from the run folder's `run.json` unless `--agent-model` is given. The judge reads the whole trajectory and the whole answer. Only when the prompt, counted by the served judge's own tokenizer and chat template at its `/tokenize` route, passes the context that its `/models` entry names less the reply tokens of the judge request is it cut, by the least that fits: the records nearest the middle leave first, never a write, then the texts of the kept records are headed to one length, then the answer. An endpoint that names no context, such as a router, gets no cut. `run_episodes/ --judge local` calls the same function after every episode. The driver and the checks of the cluster run order reach the judge through the declaration of `CausalDiagnosis/frameworks/AssetOpsBench/`, whose entry `local` of `JUDGES` is `episode_judge.py`, and `--judge` offers `none` and the declared judges. The truncation pass lives beside the judge in `truncation_pass.py`, which the command `truncation` of `cluster_run_checks.py` runs. The record format of `hidden/judge.json`, the rule of a reviewed call and the summary over the planned calls are `CausalDiagnosis/evaluation/metrics/judge_records.py`, which the tables and the rescoring read whatever judge wrote the record. A static answer has no trajectory, so the static agent is judged by the same function with `static=True`, which reads its answer from `answer.txt`, shows the judge no trajectory and writes `mode` `static` into the record.

`judge_finished_runs.py <folders of run folders> --model <judge> --base-url <endpoint> [--protocol single|paper] [--rejudge-failed] [--workers N]` judges every episode of a finished gym run of a model agent whose judge cell is empty or whose judge record holds no parsed review, an episode that ended while the judge endpoint was down, and rewrites the cell in `scores.csv`. A finished run of the static agent in mode `static`, the runs of ablation Sc3 and of table A3, is judged by the same rule in the judge's static mode, and a static episode without an answer is not judged, as in the run. A run whose `run.json` names no judge model, one started without the in-run judge, is judged only under the overrides `--judge-model <judge> --judge-endpoint <endpoint>`, which then judge every run. Each episode is judged inside a guard, so an episode the judge cannot judge, one whose runner left no `trajectory.json` among them, is named on the output and in the ledger event of the run while the pass goes on. `scores.csv` is written after every judged episode, so a pass that stops has written what it judged. `--rejudge-failed` judges again every record that holds a failed call, and `--workers N` judges N episodes at once in threads that share the one judge backend. A run whose agent model is the judge model, compared on the bare names, is refused. With the endpoint file of the serving job of the judge in `HYD_JUDGE_ENDPOINT_FILE`, every record names the serving identity of the endpoint and the ledger event the served name and the weights commit. A run of record is refused, with both values of each difference, when the judge differs from the judge block of the tracked serving file `serving_of_record.json` in its served name or in a field that the file declares, each against its line of the endpoint file, or, when `env.sh` sets `GPU_OF_RECORD`, in its GPU card. A development run is judged without the check.

`pending_grid_lines.py --grid <grid file> --runs <folders of run folders> [--starts sampled] [--fraction F | --replicates R ...] [--since AGENT=ISO ...]` prints the runs of a grid file that still lack a finished run, for the job that continues a grid after an allocation ended. On the test set `--fraction` names the share that the grid plays, 0.2 when neither it nor `--replicates` is given, `start_states.DEFAULT_FRACTION`. A whole share r/5 plays the replicates 1 to r, so that a later call with a larger share prints the missing replicates alone, a share below one replicate prints every line once with `--replicate 1 --fraction F`, and `--replicates` names whole replicates by hand in place of the share. A fold line of a cut look whose fold receives no combination of the cut is not pending. On the test set, which `run_grid.sbatch` plays by default, a line is one run per replicate, so the script prints every pair of a line and a replicate of `--replicates` without a finished run, as the line with its `--replicate`, in replicate order and nothing else, and `run_grid.sbatch` plays a line that names its replicate once. A pair is done when a finished and complete run under the folders carries the configuration, agent and switches of the line under the start set of `--starts`, on the test set also the replicate, the rule of the replicates, the master seed and the seed pool, and started at or after the cutoff of its agent, so a run of another start set leaves the line pending. A pending pair that a run in progress plays, a run whose recorded command gives the fields of the pair, that started at or after the cutoff of its agent and whose code files are unchanged, is printed with `--resume` and its run folder, the run with the most finished episodes when two match, so that the job that plays the pending pairs takes the run up from its last finished episode. A filler and a run stopped after harness errors in a row are never taken up.

`check_grid_complete.py [--starts development] <grid folders>` checks, before a push, that every grid folder holds complete runs, and writes no file. An argument is checked when it is a folder named `grid_<job id>`, and any other path, such as a manifest or a part of an archive beside the grid folders, is passed over. The grid folder must hold `job_record.txt` and, in `job_logs`, the Slurm log of its job, and a grid folder with a run of a model agent also the log of the model server and the file of the GPU sampler. Every run must hold a ledger whose check passes, so that no file is missing, changed or added without a recorded event, and a `run.json` with the code, the data and the platform, and for a model agent the serving record of its endpoint with the GPU card and the sampler. Each run must hold its planned episode folders, one row of `scores.csv` each and the files that `required_files` names in every episode folder, and the copy of the sampler file must begin with the bytes whose SHA-256 and length `run.json` records. A grid folder with a run on the wall clock must hold `in_flight.tsv`, the line per start and per end of a run or a filler run that `CausalDiagnosis/cluster_jobs/3_run/run_grid.sbatch` writes, and in each loop of the job every slot that freed after the start of the last run and before the end of the last run on the wall clock must have taken a filler run before that end. A run in progress, with a ledger of the status `running` and no `run.json`, is one problem line that names its recorded and its planned episodes and the submission that takes it up. By default a run is checked as a run of record, with no stamp, every file its driver loaded tracked at its commit and a serving record with its card, and with `--starts development` as a development run. The command prints one line per problem and ends with `CHECK_GRID_OK` and the counts of runs and grid folders, or with `CHECK_GRID_FAILED` and the count of problems.

`precompute_grid_tables.py --grid <grid file> [--config <preset> ...] [--starts <start set>] [--asset <asset_id>]` computes the tables a grid reads before its lines start, into the files the drivers read: it fits the models of the CausalDiagnosis MCP when `CausalDiagnosis/mcp_servers/Causal_Diagnosis_MCP/offline/models.json` is absent, and computes the diagnosability label table and the E18 grade table of every rules key that the lines of the grid file, the named presets and the asset-default `EpisodeConfig()` play, the configuration the gym and the OpenEnv wrapper default to, as `run_episodes/` resolves a line with its price table, and under `--starts development` through `run_episodes.development_config`, as the driver resolves that start set. `CausalDiagnosis/cluster_jobs/3_run/run_grid.sbatch` calls it before its first line, so that a fresh clone pays the computation once and no line computes a table at first use while another line writes it, and a second call computes nothing again but a label table whose engine code or asset changed since it was written. A call computes the tables of one asset, that of `--asset` (`hyd_1` by default), over which every named preset is composed and which every line of the grid file plays: the models where the model code of the CausalDiagnosis MCP can fit the asset, and the two tables where the asset declares the label of `diagnosability_label.py`, which reads both. An asset with a label of its own computes the tables that its package declares on first use.

`run_lines.py` writes the grid files of `CausalDiagnosis/cluster_jobs/` from `experiment_tables.py` and `training_variants/`, so that no run line of the cluster is written by hand. The files hold the rows of the agents table on layer 0 and the healthy control, the companion row of En9 beside them, the rungs of the ladder between the first and the last and the three rows without the CausalDiagnosis MCP on all six big layers, the baselines of the training table and the references of `h1_top`, `h2_prime` and the arms of layers 2, 3 and 5, the supporting ablations where `ABLATION_PLACES` and `ARM_PRESETS` put them, the development runs of the pilot and of the gate, and the sampling and evaluation runs of the training table. `grid_agents.txt` ends with the six rows of the agents on all six big layers and the lines of the part `layers` whose rung has layer 2 on, again on the presets of the clock mode `generated_tokens`, the parts `environment_token` and `layers_token`, then the part `misdiagnosis_price`, the ablation L1, and last the part `environment`, the three rows with the CausalDiagnosis MCP on all six big layers as released, each after every other line, so that adding them left the place of every earlier line unchanged. Every part plays on a server without LoRA adapters but the part `training`, the one part of `grid_lines.ADAPTER_PARTS`, so the two cells of every registered comparison play on one serving setup. Without an argument the command names the files that differ from the design and exits with status 1, and `write` writes them. `presets <grid file>` and `policies` print the presets and the agents of the reference runs of `CausalDiagnosis/cluster_jobs/3_run/run_grid.sbatch`, `clocked <grid file>` and `unclocked <grid file>` print the lines whose clock charges the wall seconds of thinking and the others, and `agents <folders of run folders>` prints the finished runs of the rows of the agents table, found by what they played, which `rescore_under_verifier_scope.py` scores again. `second_round <agent> <fold>` prints the sampling lines of the second round for one agent and fold, the next samples of the training configuration, as a grid file. `folds` prints the folds of the registered split, `part <part>` one part of the grid as a grid file, a part being one of `grid_lines.PARTS`, `references <part>` the reference runs beside a part as a grid file, every agent of `grid_lines.REFERENCE_AGENTS` on every preset the part names with the clock mode its lines set, and `row <id>` a grid file of one line, the row of `design.ROWS_BY_ID` on the preset `design.AGENTS_PRESET`, for one development row.

`run_health_checks.py and development_checks.py <check> <folder of run folders>` prints the checks of the cluster run order of `CausalDiagnosis/cluster_jobs/README.md` as lines for a job log and writes nothing into a run folder. `latency` prints the count, the total, the median, the p90 and the longest seconds of the model calls per run folder and pooled. `round` reads the six rows of a development round against the registered limits of `registered_analysis.json`. `pilot` prints the median of the medians of the model call seconds of the three agents with the CausalDiagnosis MCP, the measured `think_seconds_per_cycle` and `seconds_per_token`, that value over the median of the three agents' medians of the tokens generated by one model call, and the patience rule of the failure card, whose steps count the patience values played with the first and never reach the horizon of the preset. `pilot` also projects the run of record of each agent, the elapsed seconds per planned episode of its pilot run at the runs in flight of the pilot times the episodes of one run of record, with the jobs that the run needs at `design.PROJECTION_SHARE` of `design.JOB_LIMIT_S` each. A projection past that share prints `PILOT_SLOW`, a warning with the jobs of the slowest run, and refuses nothing, because a run that passes one job continues in the next from its last finished episode. The measured rates and the projection are development checks. Every run of record plays at the thinking rate and the token rate of the asset file and at the runs in flight `design.RUNS_IN_FLIGHT` that the pushed commit declares. The check refuses with `PILOT_EPISODE_TOO_LONG` and status 1 only an episode that cannot finish inside one job, when the wall limit `EPISODE_WALL_LIMIT_S` of each attempt that `INFRASTRUCTURE_REPLAYS` allows passes `design.JOB_LIMIT_S`. `gate` reads in the last round the graded Top-1 and the graded pass of the CausalDiagnosis agent against Plan-and-Execute, the share of valid diagnoses of every row without the CausalDiagnosis MCP, and the count of exact matches against the bar of the registered rule, the smallest count that an exact one-sided binomial test separates from the constant answer. The check ends with `GATE_PASS` or `GATE_MISS`, or refuses when no count separates or the bar lies at or below the floor. The pilot and the gate are optional tools, and no run of record waits for them. `cap [ASSET]` prints the `--start-cap` of a round and of a pilot. `suspect` names the runs of a requeued or a suspended job, read from the restart count of the ledger, from the job record that a grid job writes beside its runs and from the wall seconds before a tool call that exceed the monotonic seconds, and exits with status 1 when it names one. `nodes <folders of run folders>` prints the node of every run from its ledger with a count per node, so a reader sees which nodes played a table.

`rescore_under_verifier_scope.py [--own-scope] <run folders>` verifies every episode of a finished gym run again under the verifier scope `all` from the logs the run recorded, without playing the episode again, which is how En4 scores the runs of the six rows under both scopes. Every episode keeps its hidden log, its released evidence, its predictions, its grade, the cost of the oracle policy and its judge record, and gains the sensor reads per group of the greedy policy on the same seed and configuration, which `run_episodes.greedy_reference` computes as the driver does for a run started with `--verifier-scope all`. The script stops when the cost of the oracle policy differs from the one the run recorded, since the code that plays it changed after the run. The run folder stays as it is. Its copy beside it, the folder's name with `_scope_all`, holds every file of the run, with `run.json`, `scores.csv`, `summary.md` and the hidden oracle, verdict and score files of every episode written again, and the run's ledger with one event that names the run it came from and every file the rescoring changed. The copy keeps the start time of the run, so the leaderboard places it as the En4 line of the run's agent. A run that has not finished, a run without a ledger or whose files differ from it, a run of another mode than `gym`, a run already scored under the scope `all` and a run under a table whose means never read the block of the initial combination, which is a line of En15 and no main row, are refused. With `--own-scope` the script scores a run again under its own verifier scope with the verifier of this tree, the class scoring of the registered analysis, into a copy named with `_own_scope`, whose block `rescored` names the run's own scope and `own_scope` true and whose code record holds the run's lists with the list scoring of this tree, so that `index_file.py` and `pooling_rules.py` reads the copy in place of the run when that scoring list is the scoring list of the group that is read. A run that records no lists of its code is refused. Under either scope the judge cell of an episode comes from its `hidden/judge.json` when the judge wrote one, so a pass of `judge_finished_runs.py` after the run is kept.

## Statistics

`table_statistics.py` holds the statistics behind the tables. Every function takes plain sequences and returns plain numbers.

| Function | Content |
| --- | --- |
| `paired_cluster_bootstrap(a, b, clusters, resamples, seed, level)` | the mean of the paired differences with a percentile interval and a standard error from a bootstrap that resamples whole clusters, the recorded blocks, since episodes that share a block share most of their cycles |
| `sign_flip_p(differences, clusters, flips, seed, whole)` | the two sided p value of the mean of paired differences from a sign flip test over whole clusters, the share of the assignments of signs to the clusters whose total lies at least as far from zero as the observed total. A cluster whose differences sum to zero changes no assignment and is dropped. With `whole` set the sums are whole numbers, as the differences of a zero or one outcome give, and the share is exact by convolution over the clusters, whatever their number, with no random draw. Without it every assignment of the G remaining clusters is enumerated when 2 to the power G is at most `flips`, which is exact, and otherwise `flips` random assignments are drawn with an add one share. Every p value of the tables comes from it, with `whole` set for every zero or one outcome, top-1 and pass among them, so the choice follows the kind of the outcome and never the data |
| `majority_share(labels)` | the count of the most frequent label and the number of labels, `(0, 0)` for none, the score of the constant answer that the baseline of the exact match of the faulty set reads |
| `binomial_bar(n, right, alpha)` | the smallest count of `n` episodes that an exact one sided binomial test at level `alpha` separates from a constant answer right in `right` of them, the upper tail under the rate of the constant answer at most `alpha`, summed in whole numbers so that no rounding decides a count at the edge, and none when no count separates, the bar of the exact match that `cluster_run_checks.py gate` reads |
| `cluster_bootstrap(columns, clusters, statistic, resamples, seed, level)` | a statistic of sums over items with the same clustered interval and its standard error, the standard deviation of the resampled values. `columns` holds one row per item and one column per summed quantity. The sums of every resample are one matrix product of the counts of `resample_counts` with the sums of each cluster, and `statistic` returns one value per resample by array arithmetic. A resample without a value, as one that counts no item, is dropped, and the result names the clusters, the items and the resamples used |
| `resample_counts(n_clusters, resamples, seed)` | how often each cluster is drawn in each resample, a resample being as many draws with replacement as there are clusters. The matrix is drawn once per number of clusters, number of resamples and seed from numpy's PCG64 generator, so every statistic over the same number of clusters reads the same resamples |
| `ratio(sums)`, `kappa_of_counts(sums)` | the two statistics of `cluster_bootstrap` that the tables use. The first is the first column of sums over the second, which is a mean, a share or a ratio of two means. The second is Cohen's kappa of two yes or no ratings from the counts of their four pairs of answers |
| `cluster_proportion(hits, clusters, counted, resamples, seed, level)` | the share of hits among the counted items with the same clustered interval and standard error, empty when no item is counted |
| `holm(p_values, alpha)` | the Holm step down over one family: adjusted p values and rejections |
| `wilson(successes, n)` | the Wilson score interval of a proportion |
| `cohens_kappa(a, b)` | the agreement of two verdict sequences, undefined when the chance agreement is one |
| `spearman(x, y)` | the rank correlation with average ranks |

## Ablation tables

`tables_from_runs/` writes one table per supporting ablation of the paper, the GEPA table and its online curve, the tables of the six rows of the agents and the CausalDiagnosis MCP, the tables with the metrics of the AssetOpsBench paper, the two tables of the realized elimination of the paid reads, the baseline policies on the rows of the environment, the effect of each big layer, the tables of the trained agents and of what they trained on, the funnel and the failure classes of every condition, the contrasts of the designs, the pairs by faulty component, the layers of the baseline policies, the split by the first deterioration, the healthy control, the restored episodes, the families of the top layer and of the full environment, the schedule of candidate plans, the agreement of the two diagnosability labels and the table of run folders, from the run folders, as CSV and Markdown:

```bash
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis tables all [--runs CausalDiagnosis/results/runs] [--out CausalDiagnosis/results/tables] [--readme CausalDiagnosis/results/README.md] [--published CausalDiagnosis/results/published_runs] [--cluster <name>] [--resamples N] [--alpha A] [--registered <path>] [--seed S] [--index <path of INDEX.json>] [--fraction F]
```

`--fraction` names the share of the test set that the read takes, 0.2 unless it is given, `start_states.DEFAULT_FRACTION`. At a whole share r/5 every row is read on the untagged runs of the replicates 1 to r, also a row that holds more, so that every row of a table stands on the same cells, and at a share below one replicate on the runs tagged with exactly that share, whose cells print estimates without interval or standard error, since a cut look takes its combinations for coverage and not at random. A read below `counting.fraction_of_record` of the registered file marks every label partial with its share and runs no registered test. Runs off the test set, which carry no replicate, are read at every share. A row of the test set is complete only when every replicate of the read holds a finished run of each fold it plays. Every table is computed only from the run folders that exist. Without any folder the Markdown states the design of each table, what varies, the hypothesis, the metric and what a result would mean, with the header row and empty cells, and every CSV holds its header alone. Every interval, proportions included, comes from a bootstrap that resamples recorded blocks, so that the five episodes of a test combination form one cluster and a line 47 clusters, and differences between the levels of a factor are paired by episode, the same seed, scenario and every other factor, one pair per test combination and replicate, with the p values of a table's primary metric corrected by Holm. The five runs of a line on the test set, one per replicate, share no seed, so every table pools them, while a run of another commit and the earlier of two runs on a shared seed enter no table. The training variant of `run.json`, the key `training_variant`, which a `run.json` without it reads as the agent as released, is a setting of the condition of AGENTS, CALLS, STRATA, JUDGE, EFFICIENCY, PLANS and ELIM and a column of RUNS, the tables of training read it, and every other table reads the runs of the agents as released alone. The serving setup of `run.json`, the key `lora_adapters`, the LoRA adapters that the server of the agent model holds as the endpoint file of its serving job names them, 0 without the key, is a setting of the same condition with the main level 0, so every table and family but training reads the runs on a server without adapters, a pair never forms across two setups, and the tables of training read each row on one setup, the one with the adapters when a run of the row played there. Under the cross-fitting a trained run names in `run.json` the fold its model holds out, the key `training_fold`, and plays only the episodes of that fold, the fold of an episode being the one that `training.fold_of` gives its initial combination in the registered split of its asset, so a trained run without a fold or with an episode of another fold stops the script, and the tables lay out one column group per fold of the split. The presets, the six rows, the hypotheses, the places of the supporting ablations and the training variants come from `experiment_tables.py`, the one place that names them, which takes the variants and the folds from `training_variants/`.

The analysis is declared in `registered_analysis.json` beside the script, written by hand and never generated, which `registered_analysis.py` reads and `--registered` replaces. The file holds the level and the test, which `--alpha` overrides, the intervals with their resamples, their seed and the smallest number of initial combinations below which a cell prints its estimate alone, the counting rule of unscored, unjudged and unplayed episodes and of replays, the fraction of record, the families of tests with their preset, start set, measures, direction, size and tests, the groups of families that are primary, each one family of the Holm correction, the descriptive tables, the companions, the judge, and the numbers of the development steps. The primary groups are `h0`, the judge against the verifier, `agents` on the base layer, and `h1_top` with `h2_prime` in the full environment. Holm runs over the registered size of a family, or of the group of primary that joins it with another, and a test that could not be computed enters with a p value of one. The file names no component, level or count of an asset, so the counts of a table come from its start set. A value that is null is open, and a tool that needs it stops and names it. The fraction of record is a whole fraction of the replicates of the test set, 1.0, at which the read of record and the result cells of the paper read the tables. A read below it marks every label partial with its fraction and runs no registered test. The foot of `aggregate.md` and the parameters of `INDEX.json` print the SHA-256 of the file.

## Provenance

The scripts of this section tie every cell of a table to the run folders and the code behind it, so that a reader can check a number without trusting the report that states it.

`run_ledger/` writes `ledger.json` into every run folder. The driver calls it before the first episode, after every episode and after `run.json`, so a run cut short keeps a ledger with the status `running` and every episode it finished, and a later job takes the run up with `--resume`. The ledger records the outcome of the start check of the job that started the run and one event per job that took it up, with its job, its command and the episodes kept and set aside. The ledger records the command line, the Slurm job and the host, the fork's commit with the code files that differ from it, or on the cluster, where the fork has no git, the hash of the upload manifest with the code files that differ from the upload, the SHA-256 of every code file whose prefix `run.json` keeps, the model and the judge with the endpoint files of their serving jobs, the data files the run read, the configuration with its hash, the seeds and the SHA-256 of every file of the run folder but the `__pycache__` folders that Python writes beside a module it imports from there and the `.DS_Store` file of Finder, which no ledger records. Of the job's environment it copies a fixed list of names only, so no key reaches the ledger. A tool that changes a file of a finished run, a rejudge or a sync, appends an event with the old and the new hash of every file it changed, an archive move appends one without files, and nothing else rewrites the ledger. The ledger keeps the endpoints, so it stays in the run folder, which git ignores.

The AssetOpsBench reproduction writes the same ledger from its own `run.json`, with the scenario file, the CouchDB manifest and every data file the manifest names as its data, and every scoring by `score_runs.py` enters as an event that hashes the scorer code at scoring time. Two commands of `run_ledger/` serve the runs that the driver did not record.

```bash
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-ledger after <run folder> [--scorer-sha256 <file>]
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-ledger event <run folder> <tool> <what>
```

Every file that an upload ships under `src/`, `CausalDiagnosis/`, `CausalDiagnosis/frameworks/AssetOpsBench/reproduction/` and `CausalDiagnosis/cluster_jobs/`, and `uv.lock`, lies in one list of `design.CODE_LISTS` or in the agent lists of `design.AGENT_LISTS` alone, by path rules that name no asset, and `design.lists_of` gives the lists of a path. A list has one of three roles. The role identity marks a list whose files can change an episode or its score, so that the list enters the identity of a run, as `episode`, `scoring`, `harness` and the list of the run's agent do. The role bound marks a list whose files no run loads while a registered number or record depends on them, as `analysis`, `reproduction` with the acceptance of the two ports, `cluster` with the files under `CausalDiagnosis/cluster_jobs/` that no earlier list holds and the lists of the other agents do. Of the files under `CausalDiagnosis/cluster_jobs/`, the training scripts and `requirements-train.txt` lie in `training`, the pages in `documents` and the tests in `checks`. The role free marks `checks`, `documents`, `rendering`, `training` and `upstream`. The start check binds the first two roles through the commit, and the group key of the tables through the hashes of the lists. A cluster script moves neither the identity of a run nor the group key, while the start check still pins it through the commit. What such a script hands a run is recorded apart from the code, the options of the run line in the configuration, the variables that the servers read under `server_env` of `run.json`, the runs in flight, the serving flags and the card under `serving`, the processors and memory of the job under `granted`, and the `HYD_*` and `GRID_*` variables of the job, `MODEL` and `SERVED_NAME` among them, under `command.env` of its ledger event.

```bash
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-ledger platform --out <file> [--facts <data file>] [--model <served name>] [--judge-model <served name>]
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-ledger record-check [--facts <data file>] [--asset <asset id>]
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-ledger serving --shell [--role agent|judge]
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis experiments run-ledger serving --check <endpoint file> --role agent|judge [--mode alone|co_served]
```

`platform` writes the platform record of the node it runs on, what a run records there as `platform` and `data`, and the serving identity of the endpoints whose files `HYD_ENDPOINT_FILE` and `HYD_JUDGE_ENDPOINT_FILE` name, each with the GPU card of its serving job and under the served name of its file unless `--model` or `--judge-model` names another. The job hands the registered setting of each model, its served name, its Hugging Face id and its pinned revision, as `HYD_MODEL`, `HYD_HUB_ID` and `HYD_REVISION` for the agent and `HYD_JUDGE_MODEL`, `HYD_JUDGE_HUB_ID` and `HYD_JUDGE_REVISION` for the judge, and the record takes them as `model`, `hub_id` and `revision`, so it names the judge after the judge job has ended. A setting that differs from the line `served_name`, `model` or `weights_commit` of its endpoint file, or that has no endpoint file, stops the command before it writes. `record-check` reads the rules of the start check that need no run line and no endpoint, rules 1, 2, 4, 5 and 6, with an open field of the serving file of record as a reason, and prints `RECORD` with the commit or `DEVELOPMENT`, each followed by one line `REASON` per reason. `record-check` calls no model, writes nothing and exits 0 in both cases. `serving --shell` prints the serving file of record as shell assignments, `CD_AGENT_` and `CD_JUDGE_` followed by the field, and exits 3 with the reason when the file is missing, a field is null or a weights commit is not 40 hex digits. `serving --check` compares an endpoint file with the block of its role and prints `SERVING_OK` or `SERVING_DIFFERS` with one line per difference.

`after` writes the ledger of a finished reproduction run that has none, from its `run.json` and its files as found, says in the ledger that it was written after the run, and enters the judge records and scores already in the folder as one event, with the scorer code as the given lines of sha256sum hash it. `event` appends an event without files, for a tool that moves a run folder instead of changing its files.

The cluster's copy of the fork is an upload without git, so the upload script writes `UPLOAD_MANIFEST.txt` into it, one line of sha256sum per file, and every ledger keeps the manifest's hash. On the laptop, `python -m CausalDiagnosis experiments upload-manifest match <manifest>` names the commit whose files equal the manifest's, or the nearest commit with the files that differ. The sync of the run folders hashes every file on both sides through `check_synced_runs.py`, stops when a file of a finished run differs after the copy, and gives every finished run with a ledger one event that names the source and the files the sync replaced. The event goes to `local_events.json` beside the ledger, which remains byte for byte the cluster's, so a second sync fetches nothing and an event written on the laptop survives it, and `ledger.load` returns the events of both files in time order. An upload ships no generated table, since the fitted models, the grade table and the label table are computed on the cluster before the first line of a grid. Nor does it ship the key file `.env` or, in `CausalDiagnosis/cluster_jobs/`, the settings file `env.sh`, which holds the key of a remote judge and of which the cluster keeps its own, and the local grid files `local_*.txt`, all of which git ignores.

A sampling run of fine tuning, whose `run.json` has the mode `training`, enters no table, since its episodes are training data. A run of record carries an identity and no stamp, a development run carries the stamp, and a run written before the identity carries neither, and a root that holds runs of record beside runs of another kind stops every table tool. In a root of runs of record the runs fall into groups by their key, a shared part, which holds the hashes of every identity list that is not an agent's own, the data record, the digests of the generated tables read, the serving identity, the card and, for a preset with the wall clock, the runs in flight and the processors and memory granted to the job, and an agent part, which holds the hashes of the agent's own lists. A run outside a Slurm job records null resources, so on the wall clock it never pools with a run of the cluster. A run that a later job took up is two identities and is left out when that job served its model otherwise than the first job, or, on a preset with the wall clock, when the scheduler granted that job other processors or memory than `run.json` records, as the resume event of the ledger holds. In a root of development runs a run of another identity or another GPU card than the latest start of its agent is left out. In a root of runs written before the identity a run of another commit than the run with the latest start is left out. In the last two kinds the earlier of two finished runs of one condition that share a seed, as when a line of a grid is played again, is left out, so the later start alone counts, as the leaderboard chooses. A page or a table file of a development root opens with the line `Development runs. Not results.`, and no table tool writes such a root into `results/` or below it, while a page of a root of record opens with the commit or commits and the hash of the shared part that was read, so that a table of older folders never passes for one of record. `publish_runs.py` and `run_review_pack.py` refuse a development root. `tables_from_runs/` prints every run it leaves out this way on its standard error, and `leaderboard.py` lists them under the counted runs of its page. `leaderboard.py` adds the run it chose for every line of the page, the other candidate runs, the rule that chose it and the counted runs it left out with the reason. `paper_tables/` adds its two files and the row of an aggregate table behind every line of the main tables. The index holds names and hashes and no reading.

## The online loop of GEPA

`gepa_prompt_optimization/` runs the online loop of GEPA over one tunable block of text, the same for the three agents of the training table, AssetOpsBench's Plan-Execute, the Agent-As-Tool of the AssetOpsBench paper and the CausalDiagnosis agent, each with the CausalDiagnosis MCP. A candidate holds the block alone, of any length, which the agent receives appended to the task message of the episode through `training.with_task_block`, the briefing, an empty line and the block, the same position for the three agents. `question.txt` and the judge hold the briefing alone, and the episode folder receives `task_block.txt` when a block is set. The starting candidate is the empty block, so it plays the agent without a block and is the reference of the comparison. No candidate changes a prompt of an agent, its system prompt included. Every loop belongs to one fold of the split of `--training-split`, the registered split by default, the fold its model holds out, which `--training-fold` names, and `--training-variant ft` plays the agent with the filtered adapter of that fold, the loop whose final block the `ft_gepa` variant of the fold plays.

```bash
export API_KEY=<key>
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis training gepa-prompt-optimization --model <model> --base-url <endpoint> --reflection-model <judge model> --reflection-base-url <judge endpoint> --training-fold <fold> [--agent plan_execute|agent_as_tool|causal] [--training-variant as_released|ft] [--card verifier|score_only] [--config <preset>] [--servers rig|aob] [--store memory|couchdb] [--block 3] [--window 2] [--children 1] [--max-episodes 240] [--first-seed 0] [--master-seed 42] [--seed-pool 8] [--gepa-seed 0] [--training-split registered|development] [--facts <data file>] [--out CausalDiagnosis/results/runs] [--resume]
PATH=$PWD/.venv/bin:$PATH python -m CausalDiagnosis training gepa-prompt-optimization export <run folder> [--training-root <training folder>]
```

The rows of the training table pass `--config deterioration --servers aob`, with `--store couchdb` on the cluster, and the defaults of `--max-episodes`, `--block`, `--window`, `--children`, `--gepa-seed` and `--card` are the registered numbers of `configs/training/<asset_id>/rft.json`. The stream serves the training seeds of the loop's fold in seed order (`start_states.training_stream`), the initial states of the combinations the model of the fold trains on that no replicate of the test set plays, through `start_states.training_start_states` under `--master-seed` and `--seed-pool`, under seeds that are no reserved seed and no label rollout. Per training initial state the stream passes over every seed that the sampling of a round of the fine tuning of that fold may play, the samples of the first round and of the extension rounds of `rft.json` (`training.sampled_per_state`), so no loop scores a block on an episode that an adapter may have trained on, and the loop on the base weights and the loop on the adapter read the same stream. A loop plays training initial states alone, and the comparison of its final block with the starting block is read from the evaluation runs of the variants, which play the test set once. Round r takes the next `--block` seeds of the stream, and every member of the front and every child proposed after the round before plays each of them, paired by seed. The score of a stream episode is the verifier's reward with the declaration credit set to zero, `STREAM_DECLARATION_CREDIT`, the pass alone in the outcome term, so that a candidate cannot climb the stream by declaring, and an episode that the verifier could not score enters no mean and is counted apart. A stream episode whose hidden log reaches a single fault of the fold the loop's model holds out scores nothing, no reflection call reads it, and the record counts it. The point of the online curve for a round is the mean score of the incumbent fixed after the round before on the block of the round, so every point rests on episodes that no step of the optimizer has seen. A child joins the front when its mean on the block exceeds its parent's. Over their episodes of the last `--window` rounds the front retains the candidates that lead some stratum, a stratum of the STRATA table or the whole block, less any candidate that another strictly dominates, and the incumbent is the member with the best mean. The reflection model then proposes `--children` children, each from a parent drawn from the front with weights equal to the strata it leads. A child is proposed only when the next round can pay for it, the loop stops before a round that `--max-episodes` or the stream cannot pay. The loop is written out in the module rather than run through the gepa package, whose optimize call works on a fixed split of training and validation sets. A proposal whose two attempts both end on an error of the reflection endpoint is unanswered, and `unanswered_proposals` of `rft.json` such proposals in a row end the loop with the status failed, the line FAILED and the exit status 1, while a refused text counts as an answer. The loop writes its whole state after every round, and `--resume` takes up the unfinished loop of the same settings, asset, split and code under `--out`, moves the episodes of a round cut short to `interrupted/` inside its run folder, counts them in the record and plays their seeds again, starts a new loop when there is none, stops when there are several, and plays a finished loop never again.

Per episode of the parent on the block, the reflection model reads the question, the agent's outputs as the run folder holds them for every agent, its written plan, `plan.txt`, or the steps of the Agent-As-Tool supervisor in `react_trajectory.json` without the sub-agents' replies, then the closing answer, and the feedback. Under `--card verifier` the feedback is the feedback card of `gepa_prompt_optimization/feedback_card.py` that the next paragraph describes, and under `--card score_only` it is the score alone, the control, so the two arms differ in the feedback only. The number on both cards is the score of the stream, the reward with the declaration credit set to zero, the number the selection uses, so the reflection model never reads a credit for declaring that the loop does not pay. A mutation sends the meta prompt of GEPA word for word with the current block, empty at the start, and one closing paragraph that says where the block goes, that an empty block means no instruction so far, and that the instruction comes within ``` marks. No rule bounds the length of a block, so a block that leaves the agent no room in the served context ends the episode with the end `context`, and that episode is scored as it stands, with no diagnosis, so its outcome term is zero while the cost and delay terms of what it did still apply. That end is the pressure that selection puts on the length of a block, not a limit of the loop. A proposal without a block or equal to its parent goes back once with its problems, and a second refusal records it without an episode. The reflection model is the judge model on the judge endpoint of the job, asked at temperature zero without thinking with the request of `episode_judge.py`, and its replies have no length cap.

The feedback card, `feedback_card` of `gepa_prompt_optimization/feedback_card.py`, is the only record of a scored episode that reaches the reflection model. The card holds, per asset, the ok flag of every check, the pass, the success, the failure class, the abstention and the count of unnecessary orders, and, for the episode, the number the loop scores it by, the realized cost, the end reason, the steps, the refusals, the public trajectory with every reply whole, and the messages of the diagnostics tools. The details of the checks, the per component diagnosis, the hidden initial state, the truth at the write, the oracle's work orders and cost, the normalized cost and the seed never reach it, since they tell which components of a past episode were faulty, and the card reads no column of the driver's row. `feedback_string` writes the text that the reflection model reads from the card alone.

The run folder holds `run.json` with the mode `gepa_online`, the split under `training_split`, and a `gepa` block with the agent, the training variant, the fold, the card, the reflection model, its endpoint and request with no reply cap, the temperature, the block, the window, the children, the budget, the first seed, the generator seed, the components, the attempts of a proposal, the limit of unanswered proposals and the name of the result file, then `scores.csv` with one row per episode and its call in `gepa_call`, `ledger.json`, the episode folders `call<n>_seed<s>`, `gepa_online.json`, the block of every candidate under `candidates/` and every call of the reflection model with its prompt and reply under `reflection/`. `gepa_online.json` holds the status of the loop, running, finished or failed, the settings with the fold, the attempts of a proposal and the limit of unanswered proposals, the identity that a resume compares, the rounds of the curve, each with `round`, `rollouts` for the episodes played before the round, `mean_score` for the mean of the loop's score, `n` for the scored episodes of that mean and `unscored`, the candidates with their parent, component, status and length, every episode with its call, phase, round, candidate, seed, number of faulty components, reward, score, strata and `left_out`, then `episodes_played`, `rollouts_to_best`, the episodes played until the final candidate was first chosen, the episodes left out, the proposals asked, answered and asked without an example, the rounds that a resume cut short with their episodes, and the state that a resume restores. The loop asks the start check before its `run.json`, so a loop that the check does not register carries the stamp development, as a run of the driver does.

The export writes the final block of a finished loop to `blocks/gepa_<agent>_f<fold>.txt` of the training folder for a loop under the verifier's card on the agent without training, `blocks/gepa_score_only_<agent>_f<fold>.txt` for a loop under the score-only card there, the control, which no loop on an adapter runs, or `blocks/gepa_ft_<agent>_f<fold>.txt` for a loop on the adapter of its fold, with its record beside it, which holds the agent, the base variant, the fold, the asset, the split, the card, the run, the candidate, the SHA-256 and the length of the block, the adapter the loop played on, the candidates that played on the stream, the stream episodes, the stream episodes whose hidden log reaches a single fault of the fold its model holds out, `episodes_visiting_test_combinations`, since the stream is the training data of the `gepa`, `gepa_score_only` and `ft_gepa` columns, the stamp of the loop's run, and `built_from`, the run of the loop with the SHA-256 of its `run.json` and the runs its adapter was built from. The export refuses another loop, a loop of which the reflection model answered no proposal, whose final block is the starting block, and a second loop that would replace a different block. The `gepa`, `gepa_score_only` and `ft_gepa` variants of the driver play that block on the fold of its loop, and `ft_gepa` only on the adapter weights its loop played on.

## Training in the environment

The training table plays the three agents with the CausalDiagnosis MCP on all six big layers in six variants, which every run records as `training_variant` in `run.json`. The variants are `as_released`, the agent without training, which every table prints as no training, `gepa`, with the final block of the online loop on it, `gepa_score_only`, with the final block of the same loop run with a feedback card that carries the score alone, so that a gain of GEPA can be traced to the verifier's card and not to the reflection model, `ft`, with its LoRA adapter fine tuned by rejection sampling on the episodes the verifier passed, `ft_gepa`, with that adapter and the block of the loop run on it, and `ft_unfiltered`, with the adapter of the control, fine tuned on as many episodes drawn without the filter on the verified pass, so that a gain can be traced to the environment's signal. The tables print them as no training, GEPA, GEPA on the score alone, fine-tuning, fine-tuning + GEPA and fine-tuning on unfiltered trajectories. `training_variants/` names the variants, the folds of the split, the adapters `rft_<agent>_f<fold>` and `rft_<agent>_unfiltered_f<fold>` and the blocks of every fold, which a run reads under the training folder that `HYD_TRAINING` names, outside the fork, and checks against their records before the first episode. An adapter is sent as the model `<model>:<adapter>`, which SGLang serves beside the base model, while `run.json` holds the base model and records the adapter with the SHA-256 of its weights, both by paths relative to the training folder, and the agent's label in `scores.csv` is the same for every variant.

Training and evaluation are cross fitted over K folds, one rule for any asset and any number of faults, `CausalDiagnosis/datasets/splits/train_test_folds.py`. The single faults of the test combinations are dealt into the K folds component by component, K at most the number of single faults so that every fold holds one, and a component with fewer faults than K is faulty in that many folds only. The model that holds out a fold trains on every initial combination with no fault of that fold and none that a repair reaches, and each test combination, of any number of faults, is tested by one model among the folds of its own faults, the one that holds the fewest test combinations of its number of faults so far, a seeded draw breaking a tie. A split that leaves a model without a training initial state is refused, as a split that leaves a fold without a test combination is. `write_training_split.py` writes the split of an asset once, before any run, and the hydraulic rig is the instance with K = 2 and seed 0, the registered split `configs/training/hyd_1/folds.json` of its 47 test combinations. Its ten single fault combinations are dealt five to each fold with every component faulty in both, and a two fault combination trains a model only when both of its single fault parts lie outside the fold that model holds out, since a passing episode plays one part between its two repairs. Each model so trains on 14 combinations of the other fold, five single fault ones and nine two fault ones, while the other 19 two fault combinations train no model and are dealt for evaluation alone, ten to fold 1 and nine to fold 2, so fold 1 holds 24 combinations and fold 2 holds 23. The model of a fold trains on the 70 initial states of its training combinations that no replicate of the test set plays, five per combination, and plays only the test episodes of its own fold, so every test episode is judged by a model that never started at its combination and cannot reach it by a repair. Only a drop of the layer 5 hazard can carry a training episode to a combination that holds a single fault its model holds out, and the records count such episodes for the table of what each agent trained on. A training episode replays no reserved seed, the smallest seed of every test combination, and no label rollout, through `start_states.training_seeds`.

The development combinations of an asset are its recorded fault combinations outside the test set. The test set holds the recorded combinations that the asset's fault rule allows, and `development_split.development_starts` returns the other recorded combinations that hold a fault. When those miss a faulty level of some component, the fewest test combinations that complete the coverage move to development, chosen by the registered seed `DEVELOPMENT_SEED`, and leave the test set, which `development_split.starts_of_test_set` returns and `write_training_split.py` deals. A search for those combinations that passes its bound of candidate covers is refused. On the rig the development combinations are the recorded combinations with three or four faults, every faulty level of every component among them, nothing moves and the test set holds its 47 combinations. `run_episodes/ --starts development` plays them. The development split is the same rule dealt over the development combinations, `configs/training/<asset_id>/folds_development.json` from `write_training_split.py --starts development`, which `rft.json` names under `development_file`. Before the runs of record a trial of the training path reads development combinations alone, with `--training-split development` on its sampling lines, its loops and its evaluation lines, every run stamped development in a run folder of its own, and its data, adapters and blocks in a training folder of its own, each marked with the split, so no run of the registered split reads them. A development episode can still reach the recordings of a test combination after a repair, as every episode reaches the healthy recordings. The reserved seed of a test combination, its smallest seed, enters no test replicate and no training sample.

One round of rejection sampling per agent and fold has five steps.

1. Sampling. `run_episodes/ --starts training --training-sample k --training-fold f` for k from 1 to 17 and both folds, the k-th free seed of every training initial state of the fold, one run of 70 episodes each, at the sampling temperature in place of the agent's temperature, in the mode `training`, which no result table reads.
2. Data. `rejection_sampling_examples.py --runs <the 17 sampling runs of one agent and fold>` writes `data/<agent>_f<fold>/` of the training folder, the examples of the good episodes, those the verifier passed whose cited evidence the released record holds (`verifier.good`, the filter `good` of `rft.json`), `examples_filtered.jsonl`, the examples of as many episodes drawn uniformly without the filter, `examples_unfiltered.jsonl`, and `manifest.json` with the runs, the agent's label, the fold and the counts, among them the episodes of each arm whose hidden log reaches a single fault of the fold its model holds out. Every model call of a kept episode becomes one example, the prompt as the agent sent it and the reply, on the chat route for Plan-Execute and the CausalDiagnosis agent and on the completions route for the Agent-As-Tool, whose reply holds the stop string that ended it. A call that raised, an empty reply and a reply cut at the token cap become no example, in both sets alike, and the builder refuses a seed outside the training initial states of the fold. An episode whose hidden log reaches a single fault of the fold its model holds out leaves the data before the filter and before the draw of the control, whatever its outcome, and the command prints the count on a line that starts with LEFT OUT. The sampling runs of one agent and fold agree on the asset, the split, the configuration, the code identity, the model, its endpoint, the tool servers, the switch of the CausalDiagnosis MCP, the store, the sampling temperature and the development stamp, or the builder names the field and two runs that differ in it, and the manifest records the asset, the split, the stamp, the code identity and every run with the SHA-256 of its `run.json`.
The data step also writes its gate into the manifest. The minimum is one kept episode, passed by the verifier and holding a usable call, per training initial state of the fold's model, a count read from the asset's split, and `kept_per_training_state` and `extension_rounds` of `rft.json` set it. Below the minimum after the first round, the gate asks for a second round of the same size for that agent and fold alone, the sampling lines with `--training-sample` from `samples_per_state` + 1 to twice `samples_per_state`, and the data step then runs again on the runs of both rounds. Below it after the second round, no adapter trains for that agent and fold, `train_lora.py` refuses the data, and the evaluation lines of the fine tuned variants of that fold run unchanged and write marker runs that play no episode and record the gate and the alias, the runs without training of that fold, which the tables read in their place.
3. Training. `train_lora.py --examples <one example file> --base-model <model folder>` trains one LoRA adapter in a virtual environment of its own, `CausalDiagnosis/cluster_jobs/0_setup/requirements-train.txt`, on the examples tokenized as SGLang tokenized the requests, the date of the chat template pinned to the day of the sampling run, with the loss on the reply alone. An example longer than the maximum length is left out and counted, never cut. The trainer writes `adapters/<adapter>/` with `training_manifest.json`, the agent, the arm, the fold, the asset, the split, the stamp, the counts, the optimizer steps, the hashes of its inputs, the runs the data was built from, the end of the job with its offset from UTC and the versions of its packages. Before its first step the trainer writes `SOURCE.json` beside the checkpoints, the hashes of the examples, of the data manifest, of `rft.json` and of the trainer with the commit of the base model, and a job that starts again resumes from the last checkpoint when that record is the same and stops otherwise. `train_lora.py --smoke --base-model <model folder> --training-root <scratch folder>` makes one optimizer step on four made-up examples into a training folder that `HYD_TRAINING` does not name and prints the arguments of the trainer as the pinned release resolved them, the check of the training environment before the sampling grid.

Six loops per agent, for each fold one under the verifier's card and one under the score-only card without training and one under the verifier's card on the filtered adapter, each exported as above, with the judge as the reflection model, served by a job of its own and never beside the agent model.

## Baseline policies in process

`run_reference_policies.py` plays the five baseline policies, `oracle`, `do_nothing`, `random`, `greedy` and `declare`, in process on seeded episodes of one preset, verifies every episode with the released evidence composed by `released_from_env`, writes one CSV row per policy and seed to `CausalDiagnosis/results/runs/policies_<config>.csv`, a folder that a rule of .gitignore leaves out of the repository, since the rows are measured values, and prints whether the ordering check of OpenEnv's RFC 008 holds, the oracle's reward above the do nothing policy's on every seed. The verifier normalizes the cost of every episode by its own cost of the oracle episode from the same seed, so the base row, whose cost runs in calls, gets a reward. `policy_table` builds a new policy for every episode, so any row reruns on its own. `--asset <asset_id>` composes the preset over another registered asset, labels every initial combination with the label that the asset declares and writes to `CausalDiagnosis/results/runs/<asset_id>/` unless `--out` names a file. The greedy policy runs the reference classifiers fitted on `hyd_1`, so the rows of another asset hold the four other policies.

## Results policy and the cluster

The repository holds the result tables under `CausalDiagnosis/results/` and none of the run folders. The run folders under `CausalDiagnosis/results/runs/`, their published subsets under `CausalDiagnosis/results/published_runs/`, the fitted `models.json` and `grades.json` of the CausalDiagnosis MCP, its calibration reports `calibration_<date>.md` under `CausalDiagnosis/results/` and the environment's data folder are listed in `.gitignore`, since the run folders hold sensor readings of single cycles and the calibration reports hold values measured on the rig data. The runs happen on the cluster through the Slurm scripts of `CausalDiagnosis/cluster_jobs/` in this fork, whose `CausalDiagnosis/cluster_jobs/README.md` lists the commands in order, from the environment setup, the model download and the serving of the agent and judge models to the episode runs, judged under the protocol `paper`, the online loop of GEPA and the copy of the run folders back with `CausalDiagnosis/cluster_jobs/4_after_run/sync_runs.sh`, which checks every file on both sides and neither publishes nor aggregates. On the laptop, `tables_from_runs/` rebuilds the tables and the results README from those copies, `publish_runs.py` writes their published subset and `leaderboard.py` rebuilds the leaderboard, whose every row names the run folder it comes from.
