# v005设计与验证

## 实际问题依据

本轮已完成的Scenario1无MCP回合出现18次sensor_group传数组、21次无有效steps。Scenario1带MCP已完成维修后核验并恢复，但继续等待，直到max_steps。新完成的Scenario2带MCP回合中，模型已写出冷却器和泵故障，仍40次把无新数据的tier3读取放在第一步而被控制器拒绝；另有缺少mode等格式错误。

这些证据支持先改格式说明、当前可用信息和完成阶段提示，不支持把原因直接归为数据不足、环境没运行或必须换大模型。它们也不证明改提示一定有效。

## 本版设计

v4的执行逻辑逐字复制，不改其检查条件。新的_generate包装只在调查规划阶段替换提示，保留开局阶段。提示使用实际设备profile中的组名和组件，不写死液压机故障，也不提供隐藏状态。

当前没有未读数据且v4本来就会拒绝读取时，提示中不再把read列为当前可选下一步；前向读取、思考计时产生数据时仍列出read。没有开放的wait不会被虚构为可用工具。执行时仍由原逻辑判断模型实际提出的动作。

维修后给出已经收到的公开核验结果，并提醒根据全机恢复证据决定是否结束。finish仍由模型提出；wait仍可被选择，没有新增自动结束策略。

逐轮日志保留实际发给模型的提示、原始回复、原检查错误及执行后的公开状态。这样以后可以精确回答“这一轮为什么没执行”，不再根据no_call猜测原因。失败回复不被改写成合法动作。

## 离线验证

10项检查通过：无profile/无wait开局；实际组名与必填字段；原parser仍拒绝通道数组；已读完历史时的提示；前向/思考计时读数仍可选；无时钟时不提示wait；公开核验与finish建议不自动选择动作；逐条日志落盘；实际控制器解析失败保持拒绝且留下原文；正常调查提示可渲染并保留原拒绝原因。

原v4的11项协议检查也通过。以上均无真实模型调用，不是新的成功率或MCP收益。

## 后续评估边界

先完成当前冻结v4的24回合并归档停GPU。需要模型测试时再单独运行v005，与v004在相同场景/seed/模型下比较，分别看格式失败、实际动作、诊断、修复、核验、主动结束、成本和耗时。

三配置对照仍为PE+MCP、我们的agent+MCP、我们的agent无MCP。现有无MCP组工具较少的限制本版没有偷偷改变；因果建议的独立收益仍需后续同工具能力的消融。
