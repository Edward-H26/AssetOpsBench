## 阶段性观察：运行约6分钟

实际history和rank_root_causes已经执行多次，但公开status仍为time=0，observations仍只有首批历史数据，没有工单。这是当前运行快照的观察，尚不是最终结果。

单步执行没有立即消除重复空读。下一步需要在完整轨迹中核对模型是否明确看到了“最近一次返回0行”，以及MCP推荐的读取周期能否通过当前surface取得新数据。潜在下一版应显式区分已有历史的读取和等待新采样，展示每组可读周期与最近读取结果；不能简单强迫采用某个正确故障答案。是否实施，待本版完成后确认。

## 判断标准

先看合法动作实际执行、新读数取得、维修完工及复查是否发生，再看诊断正确和最终pass。记录MCP调用及其建议是否影响后续检查/维修；若只是增加调用次数，不算证明收益。保留两组可用工具不同这一限制。

### MCP确实提供了正确候选，但执行循环没有推进

首批5条读数之后，rank_root_causes的实际返回将`[100,100,2,130]`列为rank1，probability=0.9715655174404609，与本回合隐藏起点一致。模型回复也明确描述severe internal pump leakage。因此这一例不能归因为诊断服务器没给出正确方向。

但模型仍输出多步计划，例如`read → diagnose → order → wait`，每次都把read放第一位。v003丢弃尾部后重新规划，模型又重复从read开始；窗口没有新数据，原有5观测及cycle0不变。后续51次空读和重复排名没有增加证据。单步执行虽然绕开尾部检查，却形成了新的计划进度问题；不能把它描述为已修复控制器，也不能只归咎模型能力。

这一轮没有实际维修，所以尚未检验维修依赖、完工等待与复查的完整链条。正确候选不等于已提交正确诊断，更不等于pass。

### 无MCP组是本次debug引入的bug

`protocol.progress()`在profile尚未读取时访问`board.forward_read`。无MCP的surface不提供wait，属性继续调用`durations_of(None)`，触发NoneType.get异常。已在本地用`Board(reads_take_time=False, unserved={'wait'})`精确复现相同调用栈。MCP组因wait可用而走了提前返回分支，掩盖了这个开局问题。

因此无MCP组不得计为模型失败，不得用于判断带MCP优于/劣于不带MCP。此前8项协议测试缺少这个无profile、无wait的组合。
