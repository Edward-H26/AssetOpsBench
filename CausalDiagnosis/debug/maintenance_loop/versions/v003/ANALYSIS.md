# v003 设计与分析

## 待检验的问题

整计划拒绝是否阻塞了本来合理的下一步？明确公开进度、每轮执行一步后，模型是否能完成诊断、维修和复查？诊断MCP的排名、检查建议及干预预测是否实际参与决策？

## 本版修改

仅debug入口启用：每轮只执行模型提议的第一步，尾部记录但不执行；首步仍过原检查器。提示诊断提交状态、工单创建/预计完工/当前状态、wait是否可用、前向读取能否推进时间。没有注入隐藏状态，未修改维修规则、评分或预算。

冻结代码在source/，SHA256见version.json；同一版本运行时不修改source。

## 运行

固定Scenario2007、seed0，依次MCP和无MCP。模型Granite3.3-8B BF16、context131072。运行目录由UTC时间戳生成，原始交互写入runs/，不随仓库发布。

## 判断标准

先看合法动作实际执行、新读数取得、维修完工及复查是否发生，再看诊断正确和最终pass。记录MCP调用及其建议是否影响后续检查/维修；若只是增加调用次数，不算证明收益。保留两组可用工具不同这一限制。

## 下一版设计

1. profile读取前，`protocol.progress()`访问`board.forward_read`；surface不提供wait、读数不耗时且时钟运行时，该属性调用`durations_of(None)`而抛出异常。修复这项访问，并新增无profile、无wait开局组合的回归检查。
2. 不再默默丢弃所有计划尾部：明确区分模型计划、已执行进度以及新观测。可比较保留尚未执行且仍通过原检查的计划步骤，与严格单步输出的恢复方式；不能强制选择正确诊断来制造成功。
3. 显式展示最近read的返回行数、可读周期及是否取得新观测。需要新采样时，模型必须选择实际可用的等待/前向读取路径。
4. 区分MCP提供正确排名与agent实际利用建议，先跑通维修和复查，再评价独立诊断收益；保留工具可用性混杂的限制。
