# 环境与 agent 增量 debug 记录

目标：让 agent 在真实运行的环境中完成取证、诊断、维修、等待完工及复查，并分析诊断 MCP 是否帮助决策。失败保留，不通过修改标准制造成功。

## 记录约定

- 每次行为修改建立新版本，source/ 冻结；同版本可有多个 runs/，每次运行单独目录，不覆盖旧结果。
- 每个版本的 ANALYSIS.md 记录问题、证据、修改和下一版设计；每次运行的 README.md、summary.json 记录实际结果，原始输入输出、工具交互、计划及评分保留在下层。
- 正式环境、工具契约及 verifier 不变。debug 的单步控制器属于新变体，不能冒充原 agent 的正式成绩。
- 进程成功、工具能调用、诊断正确、维修恢复和最终 pass 分开记录。回合超时、网络/API错误单列。
- 当前 ±MCP 对照还改变了部分工具可用性，诊断信息的独立收益尚不能据此确认。

## 2026-11-20：从历史结果得到的设计

v001 证明开局协议可以通过 prompt 改善，但整计划检查会让错误尾部挡住合理前缀。无MCP那次已有正确诊断和未完成工单，仍重复诊断/下单，说明维修进度没有被有效用于规划。

v002 证明“让模型先读到数据”可以实现；但带MCP连续39次空读仍不推进时间。无MCP组可以通过前向读取推进到cycle40，因此“没有wait就完全无法推进”的解释不成立；需要根据实际surface区分等待和前向读取。其后将设备诊断为全健康，也不能只用协议问题解释。

v003 单独测试首步执行和显式进度提示，其他标准保持不变。运行固定Scenario2007、seed0、Granite3.3-8B BF16及同一128K服务，两模式串行，不在运行中修改冻结代码。原GPU服务14011256继续使用；客户端任务不释放GPU。

下一版只能依据完成轨迹决定：若仍空读，检查窗口绑定与可用新数据；若重复写操作，检查模型收到的进度与错误恢复；若完整流程跑通但诊断错误，再分析诊断建议和传感器证据，而非放宽pass。
